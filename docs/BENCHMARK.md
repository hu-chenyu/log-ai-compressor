# Loghub 2.0 公开基准：压缩比 vs 证据保留率

> 本文所有数字来自 `scripts/benchmark_loghub.py` 在 Loghub-2.0 真实日志上的实测，
> 可复现。**包括对我们不利的部分。**

> **v2.10.0 起，这些数字有门禁在守。**
> `docs/benchmark_baseline.json` 存着最近一次全量实测的快照，
> `scripts/prove.py` 的 `claim_benchmark_table` 拿它与 README 的基准表
> **逐格对账**（容差 0.05pp）。改了任何影响聚类的代码而没重跑全量基准，
> CI 会红。
>
> 这条门禁是事故驱动的：v2.9.9 修了 `mask_text` 的两处误伤，改动本身是对的，
> 但它改变了聚类结果，于是 HPC 76 簇 / 85.1% 变成 79 簇 / 81.1%、
> Zookeeper 92.1% 变成 91.0%、Proxifier 交付口径 81.8% 变成 72.7% ——
> **README、本文与「唯一负例只差 2 个事件」全部原地不动，六道门禁全绿。**
> 与 v2.9.5 撤回的那次是同一个病：对外数字，没有任何东西在校它。
> 重跑命令：`python scripts/benchmark_loghub.py --budgets 32000 --write-baseline`

## 要回答的问题

给定一份真实系统日志，在**同样的 token 预算**下，谁留住的「事件类型」最多？

行业里都在比**压缩比**（谁压得更小）。但压缩比是个会骗人的指标：
一个工具完全可以输出 50 万 token 的"压缩结果"并宣称压缩了 9 倍 ——
而 50 万 token 对 LLM 上下文来说毫无意义。所以这里同时报两个指标：

- **压缩比** = 原始日志 tokens / 输出 tokens
- **证据保留率** = 输出中仍可识别的人工标注事件类型数 / 事件类型总数

- 它量的是**产品给多少个簇**（`top_n=20`），不是聚类分得多准。

> 并打印这一段，`tests/test_benchmark_loghub.py` 钉住「实测 ≤ 上限」。
> 跑一次 `python scripts/benchmark_loghub.py` 就能看到每个数据集的上限与达成度。

**胜负怎么判的**：一律按**事件种数**比，不比四舍五入后的百分数。
报告只有 1 位小数，0.05pp 以内的差**与舍入误差分不开**，落在容差里一律记平。
（v2.9.6 之前是直接比百分数，把 OpenSSH 一个 0.005pp 的舍入差判成了「胜」——
两边其实都是 35/38。）

> 上一版这里还有一列「本项目(默认级别, 排障)」，本版**不再列出**：
> 那 10 个数是带着 v2.9.5 已撤回的覆盖率 bug 测的。现在要它请跑
> `python scripts/benchmark_loghub.py`，那一行还在输出里。

上一版写的是「5 个数据集全部第一」。那句话当时是真的，但那 5 个是
**在能连上 zenodo 的环境里挑的**，挑不出「会输」的那几个。补测之后结论变了，
这正是把覆盖面从 5 扩到 10 的代价与价值：**数字变难看了，可信度变高了。**

### v2.9.5 撤回经过：指标在数用户没收到的东西

上一版这张表写的是「严格档 10 胜 0 平 0 负」。**该结论已撤回**，理由如下 ——
这一节保留原文与数字，不修饰，因为**撤回过程本身就是这个项目的一部分**。

**病根是 `top_n: 0` 不等于「不限簇数」。** 两处错叠在一起：

1. 调用方传 `top_n: 0`，而 pipeline 里是
   `top_n = top_n if top_n else FilterConfig.defaults().top_n` ——
   **0 是 falsy，回落到 `DEFAULT_TOP_N = 20`**。「不限簇数」从来没生效过。
2. 覆盖率却按 `result.clusters` **全部**统计。

于是**指标和它描述的文本是两个不同的对象**：

| | 覆盖率数的是 | 报告里显示的是 |
|---|---|---|
| 默认档 | 全部 93 个簇 | 只有 20 个 |
| 「严格档」 | 全部 **1,831** 个簇 | 只有 20 个 |

实测：OpenSSH 在所谓严格档下切出 **1,831 个簇 / 38 种事件（每种 48 个簇）**，
覆盖率因此报到 100% —— 而报告只有 **809 个 token，装不下 1,831 行**。
**那不是保住证据，那是把证据堆在内存里。**

**同类 bug 在同一个仓库里出现过三次，形状完全一样：**

| 版本 | 错 | 共同形状 |
|---|---|---|
| v2.9.2 | `discover()` 只扫一个根目录，fetch 解到另一个 | 断链的一端没人发现 |
| v2.9.3 | `ALL_LEVELS` 手写，漏 `FAIL`、收三个死别名 | **让数字朝好看的方向偏** |
| v2.9.5 | `top_n=0` 被当 falsy，覆盖率按全量统计 | **让数字朝好看的方向偏** |
| v2.9.6 | 拿四舍五入的百分数判胜负 | **让平手显示成赢** |

四次都是「**一个对外数字，没有任何东西在校它**」。修法不是改措辞，是加门禁：
覆盖率 ≤ 实际展示的簇数、全量口径 ⊇ 交付口径、`ALL_LEVELS` 等于规范词表、
胜负按计数比。

### 三档相似度全测（v2.11.4）：那个 97.3% 复现了，而它本来就是废的

上面那次撤回留下一个很难解释的形状：**赢过 HPC 的那一档，从此后不再出现在
任何一张表里。** 外部评审据此指控「只报对自己有利的那一档」。

指控的**动机猜错了**（撤回的理由就写在上面，动机恰恰相反），但**形状是真的**，

**三件事必须一起说，单独说任何一件都是误导：**

1. **v2.9.4 那个 97.3% 一格不差地复现了。** 测量没错，错的是口径。
   严格档在全量口径下确实赢 Drain3，也确实赢本工具自己的标准档。
2. **它赢的全是报告装不下的簇。** 严格档切出的簇数是标准档的 2–15 倍：
   OpenSSH **1438 vs 94**、Mac **1113 vs 709**、Proxifier **860 vs 115**、
   Linux **664 vs 423**。而报告只给 20 个。于是它在全量口径赢 8 次，
   在交付口径**一次都没赢**。v2.9.5 那句「把证据堆在内存里」，在另一个数据集上
   被完整复现并量化了。
3. **交付口径的赢家是 lenient，而本项目不会因此改默认值。** lenient 在 10 个
   数据集里赢 5 个、输 1 个。可是 lenient 的簇更粗 —— 20 个粗簇当然覆盖更多
   事件类型，**代价是簇内根因更不准**。把默认值改成 0.70 会让这张表好看，
   同时让产品变差：这正是 `AGENTS.md` §2.3 禁止的「对着评测集调参」，也是
   [`AUDIT.md`](https://github.com/hu-chenyu/log-ai-compressor/blob/main/AUDIT.md)
   **形态六**的又一次现身。默认值保持 0.85，这条摆在这里由读者判断。

一个诚实的补充：本项目**至今没有**按 Loghub 的标准解析协议（PA / GA）评过
自己的聚类。「换个不是你设计的指标，你还敢跑吗」——现在的答案是**没跑过**，
这是已知缺口，不是已完成项。

### 剩下的负例及其病因（v2.9.8 更新）

先更正 v2.9.2 的一处**误判**：当时把 OpenSSH 写成「过度合并」，实测是错的 ——
那 11 个未覆盖事件里有 10 个的行数**根本没进簇**（约 43 万行，占 68%），
不是被合并，是被 `ALL_LEVELS` 漏掉的 `FAIL` 档整批丢弃。真因在测量工具，
修掉之后 OpenSSH 从 71.1% 变成 **92.1%，与 Drain3 打平**（不是赢）。

**同预算档只剩一个负例（HPC）。Mac 在 v2.9.8 翻正、v2.10.0 又涨了一截：**

**① HPC 81.1% vs Drain3 87.8% —— 簇粒度比标注粗，且修法被证明不存在**

79 个簇 / 74 种事件 / 覆盖 60（81.1%）。**14 个未覆盖事件全部落在 12 个过度合并
的簇上** —— 覆盖率按每个簇的样例记一种事件身份，被合并的簇只能算进一种。

| 簇的掩码模板 | 样例事件 | 吞掉的 | 只差 |
|---|---|---|---|
| `N node-N action start N N wait (command N)` | E58 | E57 / E49 | `wait` vs `boot` / `risBoot` |
| `N gige4 gige temperature N N critical` | E65 | E74 | `critical` vs `normal` |
| `N Interconnect-1T02 switch_module control N N power/control ok` | E51 | E44 | `ok` vs `problem` |
| `N Interconnect-1T00 switch_module bcast-error N N Link error` | E63 | E72 | `error` vs `ok` |
| `N node-N node psu N N psu failure\ ambient=N` | E46 | E47 | `psu` vs `fan` |

模式高度一致：**样板逐字相同，只差一两个字面词元**。而 41/44 字符的模板让
`boot (command 1894)` 与 `risBoot (command 1899)` 的编辑距离相似度高达 0.965 ——
样板把区分词淹没了。**簇粒度比标注粗时事件就"看不见"了。**

**两次修法都失败了：**

1. **加「字面词元集合相同才准合并」守卫**（v2.9.8）：覆盖率 85.1% → 93.2%，
   **但报告从 76 个簇炸成 2,690 个、交付口径从 23.0% 崩到 8.1%** —— **已撤回**。
   这是典型的「**指标涨了但产品崩了**」：那不是更好的工具，是坏掉的工具。
2. **按数据集自适应粒度**（v2.9.8 的结论，v2.10.0 真的走完了）：不是调参问题，
   见下。

**② v2.10.0 把「自适应粒度」证伪了 —— 结论是判据不存在**

换了个问法：不猜规则，改为**先量**。把 `_find_similar` 的每一次合并决定都记下来，
用 Loghub 人工标注判定「这次合并对不对」，再去找能分开两类的特征
（`python scripts/diagnose_merge_decisions.py`，共 4,142 次决定）：

| 数据集 | 类别 | 次数 | 字符相似度 min/中位/max | 词元 Jaccard min/中位/max |
|---|---|---:|---|---|
| HPC | 该合并 | 2,193 | 0.851 / 0.923 / 0.994 | 0.273 / 0.750 / 1.000 |
| HPC | 不该合并 | 67 | 0.861 / 0.899 / 0.971 | 0.333 / 0.429 / 0.889 |
| Proxifier | 该合并 | 1,390 | 0.850 / 0.899 / 0.997 | 0.600 / 0.846 / 0.920 |
| Proxifier | 不该合并 | 492 | 0.850 / 0.899 / 0.971 | 0.529 / 0.750 / 1.000 |

**两个特征都完全重叠，没有任何一个相似度量能把两类分开。** Proxifier 里甚至有
Jaccard = **1.000**（字面词元集合完全一致）却被 Loghub 判为不同事件的合并：
E6/E7/E8/E9 的区别只是「哪一个 bytes 字段带 (N KB)」。

> **所以 Loghub 的事件定义不是模板相似度的函数。** 「一条全局规则做不到两件事
> 都对」不是调参问题，是**判据不存在**。任何调阈值 / 加词元闸门的做法都不可能
> 同时对 HPC 和 Proxifier 成立。

**还必须说清楚一件事**，否则下一个人会得出错误结论：
**「按 Loghub 判对错」与「对用户好不好」不是同一个问题。** Proxifier 1,882 次
合并里有 492 次按 Loghub 标准是错的，而它的同预算覆盖率仍是 100%。只看
「判错比例」调参，会把一个 100% 的数据集调坏。

要真的攻下 HPC，需要的不是相似度：可学习的消息表示、事件抽取的弱监督，
或按数据集配置的粒度参数（而最后这个本质上是拿评测集调参，本项目纪律明令禁止）。

**③ Mac：v2.9.8 58.5% → 82.9%，v2.10.0 → 90.4%**

v2.9.8 的病因不是聚类丢事件（全量口径一直是赢的），而是**报告把 406 条错误
消息当成「变更事件」**，逐条写出「错误首发在〈另一条错误〉后 Ns」并冠以
「变更关联」标题 —— 全篇 33% 的 token 花在这个假线索上。收敛后报告从
47,614 降到 31,563 token（-33.7%），同预算 32k 装下的簇从 421 涨到 668。

v2.10.0 又涨了 7.5pp，病因是另一件事：相似度回退曾经只比级别桶里
**最近 256 个簇**，长期只出现在桶尾之后的模板**永远找不到同类** ——
Mac 的 INFO 桶因此多出约 1,000 个碎片簇。改成整桶比较 + 精确长度上界剪枝后：

| 候选集 | INFO 桶 | 全量簇 | 同预算覆盖 | 分析耗时 |
|---|---:|---:|---:|---:|
| 最近 256 个（旧，有偏袒） | 604 | 766 | 85.8% | 23.5s |
| 模板字典序前 256（走错路） | 1,604 | 1,766 | **64.4%** | 25.3s |
| **整桶（v2.10.0）** | 547 | 709 | **90.4%** | **14.0s** |

**调相似度阈值能把 HPC 凑成「全胜」，本项目明确不做那种事** ——
对着基准调参得到的领先不是领先。上面已经证明：**就算把判据调松，HPC 的病根
也不是阈值**，所以那条路连"凑"都凑不出来。

#### LogsLop：加进来的那个正面竞品（v2.5.0）

[LogsLop](https://github.com/amd/logslop) 是 AMD 在 2026-07 的 ROCm 博客里开源的日志去重工具
（`pip install logslop`，零依赖），也是**目前最接近的正面竞品** —— 它同样用 Loghub
和 Drain3 做对照，并提出了 SURCL 指标。v2.5.0 把它纳入对照，因为它承认自己
在 PA 上不敌 Drain3（81% vs 99.75%），是个诚实但目标不同的工具。

对照口径对它公平：喂**原始日志行**（这是它自己文档与博客里的标准用法；
Drain 要剥离结构化头是因为它的模板抽取需要，对照时给各自应得的输入才公平）。
它保留的也是原始行，所以能按 LineId 精确回查，映射口径与 tail / grep / 本项目一致，
不存在 Drain3 那种「模板相似度」误判余地。标注覆盖率实测 **100%**（每个数据集
每一行都有 EventId），所以也不是标注稀疏导致的低估。

**结论：去重工具优化的目标（别让我看两遍一样的东西）与证据保留的目标
（别弄丢我的根因证据）方向相反。** LogsLop 会把文本相似的不同事件合并掉，
所以它在全部 9 个数据集上都低于 Drain3，且**几乎不随预算增长**：

| 数据集 | @500tok | @1k | @4k | @32k |
|---|---:|---:|---:|---:|
| Apache（LogsLop） | 37.9% | 44.8% | 44.8% | **44.8%** |
| Apache（本项目） | **100.0%** | **100.0%** | **100.0%** | **100.0%** |
| Zookeeper（LogsLop） | 15.7% | 21.3% | 23.6% | **23.6%** |
| Zookeeper（本项目） | **92.1%** | **92.1%** | **92.1%** | **92.1%** |

给再多 token 它也救不回来被合并掉的事件；而本项目在最小预算档就已到顶。
耗时上本项目也占优：HealthApp 上本项目 15.19s，Drain3 607.58s（**40 倍**）。

**10 个数据集里，同预算档 8 胜 1 平 1 负**（只剩 HPC 输给 Drain3，
OpenSSH 打平，见「剩下的负例及其病因」）。交付口径 0 胜 1 平 9 负 —— 那个数字不是
算法变差，是产品只给 20 个簇而 Mac 有 626 种事件。

### 这两个数字是怎么来的（不是算法变强了）

第一轮实测我们是 **3 胜 2 负**（Zookeeper 71.9%、HealthApp 78.8%）。用
`scripts/diagnose_missed_events.py` 逐条追查丢失的事件后发现：

> **丢的不是「聚类合并」，是「根本没解析出来」。**

ZooKeeper 用的是 `<时间戳> - <级别> [<模块>] - <内容>`，但 `generic` 规则集里
`iso_level_module` 的级别前只允许 `[` 或 `(`，不接受 `-`，于是整份日志掉进无结构
兜底：message 里保留完整时间戳、module 为空、指纹噪声大、不同事件被并簇。

HealthApp 用的是 `20171223-22:15:29:606|模块|用户ID|内容`，**非 ISO 紧凑时间戳 +
管道分隔**，同样无模式匹配 —— 时间戳解析为 `None`，**整份日志的时间直方图是空的**。

补了两条规则后（`iso_dash_level_module` / `pipe_delimited_device`）：

| 数据集 | 修复前 | 修复后 | 增量 |
|---|---:|---:|---:|
| Zookeeper | 71.9% | 92.1% | **+20.2** |
| HealthApp | 78.8% | 87.8% | **+9.0** |

**结论要老实说：这不是算法进步，是补格式覆盖的洞。** 聚类本身仍是
`difflib` 编辑距离 + 级别桶回退，没有 Drain 的前缀树和模板在线精修。
在**解析正常**的日志上（Apache / ProxIFIER 那种标准格式），我们领先的原因是
保留了每簇的原始样例行，而 Drain 只吐模板 —— 不是因为我们分得更准。

另外注意 **默认级别模式下 Zookeeper 从 11.2% 降到 2.2%**：这是**变准了**而非变差。
修复前那些行靠「消息里含 error/fail 关键词」被误捞进错误集，实际上它们是
`INFO` 级的启动日志。修复后级别被正确识别为 INFO，于是被正确排除。

「Drain3 的输出随模板/参数数爆炸，本项目有上界」——这个形状不会因

| 数据集 | 原始 tokens（旧口径） | 本项目输出（旧口径） | Drain3 输出 |
|---|---:|---:|---:|
| Proxifier | 624,518 | 743 | 317 |

## 结果四：换一个**不是我们设计的**指标（v2.11.5）

前面三节的指标全是本项目自己定义的。「簇样例覆盖了多少种 Loghub 事件」
不是任何公认指标的名字 —— 换个定义数字就变，因此它回答不了
「你的聚类放到同行里是什么水平」。

这一节第一次用**外部定义**的指标量自己的聚类：**PA / GA**。
它们由 LogParser（Jiang et al., ICSE-SEIP 2019）提出，Drain / Drain3 /
LILAC / LLMParser / LibreLog 全部在用，是这个领域事实上的通用尺子。

### 口径出自哪里（两份独立实现，互相印证）

| 来源 | 文件 | commit |
| --- | --- | --- |
| 发源地 | `logpai/logparser` 的 `logparser/utils/evaluator.py` | `10e31f3a` |
| 当前在用 | `zeyang919/LibreLog` 的 `parser/accuracy.py` | `36c8a45` |

两份的 `get_accuracy()` **逐行同构**（LibreLog 只额外把 P/R/F1 三个占位成 0，
并把「模板相等」的 PA 拆了出来）。本项目的 `scripts/eval_logparser_pa_ga.py`
是它们的纯 stdlib 等价移植。

> **一个必须记下来的命名坑**：`logparser` 自己在 `evaluator.py:46` 把这个值
> 打印成 `Parsing_Accuracy`，而它算的其实是**分组**对不对；PA 在那一版里
> 根本没实现。同一个值在两个仓库里叫两个名字 —— 这里按 LibreLog 的命名
> （GA = 分组、PA = 模板），并留下出处，免得下一个照着 `logparser`
> 读代码的人以为本表标错了。

> **论文正文没拿到**：LibreLog 论文（arXiv:2408.01585）的 HTML 全文在本机
> 三条网络路径上都取不到（urllib 超时、`web_fetch` 截断、Range 读被拒）。
> 所以本节的口径锚在**两份可执行实现**上，而不是论文措辞 ——
> 实现比措辞更难抄错，且带 commit 号可复核。

### 本协议与本项目的三处适配（不藏）

本项目是**流式聚类器**，不是逐行 parser。要接上逐行的 PA/GA 必须适配，
适配本身就是结论的一部分：

| # | Loghub 标准 | 本项目 | 为什么 |
| --- | --- | --- | --- |
| A | 每行产出一个正则模板 | 每行产出**所在簇的静态文本** | 本项目不做逐行正则抽取，聚类的产物就是「哪些行属于同一类」 |
| B | 模板形如 `Failed to connect to (.*)` | 掩码占位符 `U/H/S/P/N` 连续段折叠成 `<*>` | Loghub 地真值用 `<*>`，字符串相等要求两侧同形 |
| C | 预测侧按正则清洗（`clean_regex_content`） | **两侧共用同一个** `clean_content` | LibreLog 那套清洗是非对称的（正则侧只留非字母段），对不含正则的模板没有意义。共用一个函数意味着**任何一方都不可能靠「洗得更干净」取得优势** |

C 是最重要的一条，也是本项目相对官方实现**有意偏离**的地方 ——
照抄会把「哪边被洗得更干净」变成一个可被利用的自由度。

GA 58.18% vs 71.58%（**−13.40pp**）。逐数据集看：PA 上 6 胜 4 负
（Apache / HPC / HealthApp / Mac / OpenStack / Proxifier 胜），
GA 上 4 胜 6 负（Mac / OpenStack / Proxifier / Zookeeper 胜）。
**两个口径不一致这件事本身就是结论**，只报一个都不诚实。

> 这一行「GA 上 4 胜 6 负」的第一版写的是 **3 胜 7 负** —— 手算时漏了
> Zookeeper（99.48% vs 99.37%，赢 0.11pp）。它是被
> `tests/test_logparser_pa_ga_table.py` 从 CSV 重算出来的当场抓到的，
> 不是事后发现的。**汇总口径比逐格数字更容易写错**，因为没有哪一格
> 会因为它错而变红。

**2. 差距最大的地方是 GA，而 GA 恰是这个指标针对的东西。**
GA 量的是「有没有把同一个事件聚成一簇、且聚全了」，而本项目的
`_find_similar` 候选集是整个级别桶、按字符相似度 0.85 判定 ——
`docs/BENCHMARK.md`「结果一」里记过同一个形状的病（HPC 覆盖率 85.1%），
当时归因为「指标在数用户没收到的东西」。**现在换一把外部尺子量，同一个
病灶还在**：`boot (command N)` 与 `risBoot (command N)` 被并成一簇，
在 GA 上直接体现为少一个完整事件组。

**3. 表 A 与表 B 的落差是本节最有价值的发现。**
喂原始日志时 PA 平均 23.24%，喂 `Content` 时 61.71% —— 差了 38 个百分点。
Apache / HPC / Hadoop / OpenStack / Proxifier 五个数据集在表 A 里 PA
**恰好是 0.00%**，而同一份日志在表 B 里是 99.10% / 85.24% / 41.17% /
51.61% / 62.80%。

原因不是聚类，是**本项目的解析器不剥这些数据集的 syslog 头**
（`[Thu Jun 11 10:35:14 2009] [notice] ...`），于是每行模板都带着
那一截前缀，与地真值模板字符串不等。**这是一个此前完全没有被任何
本项目自定义指标暴露出来的解析层缺陷** —— 「簇样例覆盖率」只看
EventId 归属，头 prefix 不影响判定，所以它一直是绿的。

本节不修它：修它要先决定「哪些头部格式该剥」，那是产品决策，
而且按 §2.3 不得对着评测集调参。**把缺口量化写在这里，比改一个正则
然后宣称修好了更有用。**

**4. 本节不能证明的事**：这些数字量的是**逐行解析质量**，不是
「一份日志能不能被压成可复核的证据包」。表 B 上 Apache 99.10% 的
PA 并不意味着本项目的产出对排障更有用 —— 恰恰相反，
「结果一」量的是保留住多少可引用的原始行，那才是本项目的主指标。
两个问题必须分开看（与 v2.10.0 诊断脚本末尾那句话同一个立场）。

### 五、「能不能全胜」—— 把 GA 的失分**逐行**拆开量

这一节回答一个具体问题：

> PA 61.71% 赢 Drain3 3.65pp、GA 58.18% 输 13.40pp —— **能不能全胜？**

`AGENTS.md` §2.3 写着「不许对着基准调参」。**拿规矩挡回去等于没回答**，
所以下面全部是实测。两个脚本 `scripts/diagnose_ga_gap.py` 与
`scripts/sweep_threshold_pa_ga.py` **只量不调**：不碰阈值、不碰掩码规则、
不碰 `top_n`。

#### 为什么必须先拆，而不能只报一个 GA

`grouping_accuracy()` 的失分只有两个来源：

* 条件 (a) 失败：某个簇里混进了**不止一个** EventId → **过合并**
* 条件 (b) 失败：某个簇是「纯」的，但**没收到该 EventId 的全部出现**
  → **过分裂**

这两者的修法**方向相反**：过合并要更**严**的合并门槛，过分裂要更**宽**的。
只报一个 GA 总数，等于把两个相反的病混成一个数 —— **一个数不能指导两个
相反的修法**，所以必须拆。

> **过分裂为什么按行数而不是按事件数算**：条件 (b) 的判据是「这个簇是不
> 是该 EventId 的**全部**出现」，所以一个被摊成 k 份的事件贡献 **k 份**
> 失分。Loghub 上真实数据集正是高频事件重复成千上万次的形状 —— 一个重复
> 几千行的事件被摊成 20 簇，那几千行就全丢了。**这也是过分裂在
> OpenSSH / Hadoop 上格外痛的原因。**

**表 D · GA 的失分丢在哪一摊（输入 = `Content`，同一份地真值）**

占比列的分母是**失分行数**，不是标注行数。

| 数据集 | 我方 GA | Drain3 GA | 我方过合并 | Drain3 过合并 | 我方过分裂 | Drain3 过分裂 | 我方失分行数 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Apache | 99.31% | 100.00% | 0.0% | — | 100.0% | — | 360 |
| HPC | 79.33% | 84.33% | 31.5% | 12.9% | 68.5% | 87.1% | 88,876 |
| Hadoop | 55.66% | 92.09% | 4.6% | 58.9% | 95.4% | 41.1% | 79,800 |
| HealthApp | 66.97% | 75.09% | 82.3% | 2.6% | 17.7% | 97.4% | 70,148 |
| Linux | 23.25% | 80.21% | 6.9% | 11.4% | 93.1% | 88.6% | 18,360 |
| Mac | 81.51% | 77.98% | 50.6% | 43.9% | 49.4% | 56.1% | 18,552 |
| OpenSSH | 32.08% | 70.67% | 47.6% | 24.9% | 52.4% | 75.1% | 433,980 |
| OpenStack | 41.51% | 34.54% | 99.9% | 98.6% | 0.1% | 1.4% | 121,454 |
| Proxifier | 2.70% | 1.50% | 48.4% | 55.2% | 51.6% | 44.8% | 20,744 |

Drain3 那两格的「—」不是「占比 0%」，而是**根本没有失分**（GA 100.00%，

`tests/test_ga_gap_table.py` 对这个差别有专门一条判据。

**表 E · 全量失分的两桶合计（10 个数据集，852,661 行失分）**

| 失分桶 | 行数 | 占失分 |
|---|---:|---:|
| 过合并（条件 a 失败） | 438,085 | 51.4% |
| 过分裂（条件 b 失败） | 414,576 | 48.6% |
| 未解析成条目 | 0 | 0.0% |
| **失分合计** | **852,661** | **100.0%** |

未解析为 0 是个值得记的结果：**解析层在 `Content` 输入下没有留下任何
「没进任何簇」的标注行**（表 A 那 38pp 的落差是**模板**层面的，不是
「漏了一行」层面的 —— 见上面第 3 点）。

#### 三个结论

**1. 两桶几乎对半，而主导方向因数据集完全相反。**

* 过**分裂**为主（6 个）：Apache / HPC / Hadoop / Linux / OpenSSH / Proxifier
* 过**合并**为主（4 个）：HealthApp / Mac / OpenStack / Zookeeper

Mac（50.6% / 49.4%）与 Proxifier（48.4% / 51.6%）几乎是抛硬币 ——
**方向相反这件事在小数点后一位就翻面**，所以「多数数据集是哪一桶」这种
概括在这里不成立。

**同一个旋钮，两个方向相反的需求 —— 全局阈值原理上不可能同时满足。**

**2. 阈值取舍曲线：0.85 是**平均值**上的顶点，但没有一个数据集的顶点在它上面。**

`scripts/sweep_threshold_pa_ga.py` 扫 0.40 / 0.70 / 0.85 / 0.90 / 0.95。
它**按实例传阈值**（`ErrorClusterer(similarity_threshold=...)`），
`CLUSTER_SIMILARITY_THRESHOLD` 一个字都没改 —— 一个「顺手把默认值调成
曲线顶点」的诊断脚本读起来仍然完全正常，所以这条由测试守着。

**表 F · 相似度阈值的取舍曲线**

| 数据集 | 指标 | 0.40 | 0.70 | 0.85 | 0.90 | 0.95 |
|---|---|---:|---:|---:|---:|---:|
| Apache | PA / GA | 99.10 / 23.48 | 99.10 / 85.77 | 99.10 / **99.31** | 99.10 / 59.17 | 99.10 / 59.17 |
| Hadoop | PA / GA | 41.17 / 10.86 | 41.17 / 49.36 | 41.17 / **55.66** | 41.17 / 51.87 | 41.17 / 37.34 |
| HealthApp | PA / GA | 89.25 / 4.71 | 89.25 / 37.84 | 89.25 / 66.97 | 89.25 / **67.19** | 89.25 / 64.68 |
| Linux | PA / GA | 15.87 / 4.80 | 15.87 / **60.20** | 15.87 / 23.25 | 15.87 / 20.91 | 15.87 / 21.19 |

（Apache 全程 99.10、Hadoop 41.17、HealthApp 89.25、Linux 15.87）。
这一条顺带否掉了「PA 赢是因为模板拆得碎」这个假设：PA 赢在模板文本本身，
与聚类的松紧无关。

#### 0.85 是平均值上的顶点，但**不是任何一个数据集的顶点**

这是本节最容易被写错的一句话，所以单列一段。

* Apache 的 GA 顶点在 **0.85**（99.31）
* Hadoop 在 **0.85**（55.66）
* HealthApp 在 **0.90**（67.19）
* **Linux 在 0.70（60.20）** —— 而 0.85 时只有 23.25，**差 36.95pp**

最后一行是关键：Linux 在 0.70 与 0.85 之间的差距，比它与 Drain3 的总差距
（23.25 vs 80.21）还大。所以「Linux 追不上 Drain3」这句话**本身就是不完整的**
—— 它追不上是因为**默认值对 Linux 特别不友好**，而不是 Linux 这个数据集
天生难。

但**不能**因此把默认值改成 0.70：算术平均那一行是 58.29（0.70）对
**61.30**（0.85）。统一调到 0.70 的账是 Linux **+36.95pp**、HealthApp
**−29.13pp**、Apache **−13.54pp**、Hadoop **−6.30pp** —— 净亏。

所以 0.85 的地位是：**四个数据集折中出来的一个平均值顶点**，
不是任何一个数据集自己的最优。逐数据集的最优阈值散在 0.70 / 0.85 / 0.90
三个位置，**而「哪个更好」取决于你按哪个口径算**。这比「0.85 就是顶点」
更接近实情，也是不能靠调参解决的原因。

> 簇数随阈值的变化同样说明问题：Hadoop 从 0.85 的 356 簇涨到 0.95 的
> **1,132 簇**，而 GA 掉到 37.34 —— 调紧不产生更多「更对」的分组，只产生
> 更多「更碎」的簇。

**3. 真正的差距集中在 3 个数据集，全是过分裂。**

| 数据集 | 我方 GA | Drain3 GA | 我方主导失分 |
|---|---:|---:|---|
| Linux | 23.25% | 80.21% | 过分裂 93.1% |
| OpenSSH | 32.08% | 70.67% | 过分裂 52.4% |
| Hadoop | 55.66% | 92.09% | 过分裂 95.4% |

这三条要追上得动**掩码粒度或级别分桶** —— 簇的键是 `(level, msg_tp)`，
`_find_similar` 只在**同级别桶**里搜。这是**结构问题，不是阈值问题**，
本节不去动它（理由见下）。

**但 Linux 那一行要打个补丁**：表 F 显示它在 **0.70** 时 GA 是 **60.20**，
不是 23.25。也就是说 Linux 的差距里有**一大块是默认值造成的**，
追到 80.21 的路只剩 20pp 而不是 57pp。**Hadoop 方向相反** —— 它在 0.70
掉到 **49.36**，比 0.85 的 55.66 还差 6.30pp。

**OpenSSH 则压根不在表 F 里**（五档曲线只扫了 4 个数据集），所以这里
**单独补测**（`scripts/sweep_threshold_pa_ga.py --datasets OpenSSH
--thresholds 0.70,0.85`）：

**表 G · OpenSSH 的阈值补测（表 F 没有扫它，故单列）**

| 阈值 | PA | GA | 簇数 |
|---|---:|---:|---:|
| 0.70 | 31.02 | **34.68** | 34 |
| 0.85 | 31.02 | 32.08 | 171 |

**0.85 那一档是故意带的阳性对照**：它复现出 32.08 / 171 簇，与表 D 里的
OpenSSH 行逐位一致，所以上面那个 34.68 不是跑歪了的结果。

也就是说 OpenSSH 换成 0.70 **只涨 2.60pp**，对这个数据集**基本不敏感**，
而 Drain3 在 0.85 就能拿到 70.67 —— **差距是结构性的，与阈值无关。**

所以更准确的说法是：**三条差距里，只有 Linux 那一块是参数选错了；
OpenSSH 与 Hadoop 换成 0.70 都追不上**（一个几乎不动，一个反而更差）。
而「哪个数据集该用哪个阈值」本身不是产品能回答的问题 ——
真实用户给的是一份日志，不是十个数据集。

> **本节此前有一句错的话，已撤回**：原文写「OpenSSH 与 Hadoop 则相反 ——
> 它们在 0.70 时分别掉到 60.20 与 49.36，都比 0.85 差」。
> **60.20 是 Linux 的值，被原样写进了 OpenSSH 那一格** —— 而 OpenSSH
> 当时**根本没被扫过**。补测之后真值是 **34.68**，方向也是反的
> （34.68 比 0.85 的 32.08 **高** 2.60pp，不是「都比 0.85 差」）。
> 错因与仓库里已记过的那一类完全同形：**结论的适用范围比采样范围宽** ——
> 扫了 4 个数据集，却给第 5 个报了数。新增门禁 `test_ga_gap_table.py::
> test_threshold_claims_only_mention_swept_datasets` 守着这一类。

#### 结论：做不到，而且不是规矩挡人

「把 GA 调上去」和「保住 PA」是同一个旋钮的两端，而**每个数据集在这条
曲线上的顶点位置还不一样**（Linux 在 0.70、Apache/Hadoop 在 0.85、
HealthApp 在 0.90）。任何号称「全胜」的改法要么是在另一个指标上退让，
要么是**挑一个只对某些数据集好的阈值**、把其余的牺牲掉；要么动的是结构。
后者要按缺陷修，并全量重跑 10 个数据集说明「哪些变了、为什么」——
而不能靠挑一个让评测集变绿的点，那正是 §2.3 禁止的、
也是 v2.9.8 已经干过一次并被撤回的事。

**这一节不改产品。** 它把「为什么不能全胜」从一句规矩变成了一张有对账的
表 —— 而一句规矩谁都可以不认。

#### 两个被实测否掉的假设（如实记下）

* **「256 簇比较窗口太小」** —— v2.10.0 已经**整个去掉**了
  （`clustering.py::_find_similar` 的 docstring 里有完整实测表）。
  它是个早已排除的嫌疑，不该再被当成改进方向提一次。
* **「PA 赢是因为模板拆得碎」** —— PA 对阈值完全不敏感，与聚类松紧无关。

## 结论（诚实版）

**1. 证据保留率（同预算 32k）10 个数据集里 8 胜 1 平 1 负 —— 而那些胜里的领先是"补洞"补出来的，不是算法更强。**
真正的算法差距仍然存在：我们的聚类没有前缀树剪枝、没有模板在线精修。
在**解析正常**的日志上领先，是因为我们为每簇保留了一行原始样例作为可引用证据，
而 Drain 只吐模板 —— 样本行天然覆盖更多事件类型，但这不等于「分得更准」。
交付口径 0 胜 1 平 9 负、全量口径 8 胜 1 平 1 负，三个都报，见结果一。

**1b. 剩下的落后写明了病因**（HPC：极短通用消息被并簇），不是「随机波动」——
**一个能被解释的失败，比一个无法解释的成功更有用**，但那前提是它被写在明处。

**2. 我们赢在"输出规模有上界"。** 无论日志是 2 万行还是 21 万行、11 种还是
156 种事件类型，summary 输出都在数百 token（复测 313–788）。这直接决定了
它能不能塞进 LLM 上下文。

**3. 这仍然是一条工程性质，不是护城河。** 给 Drain3 加一个 `--max-clusters`
十分钟就能做到。**能被十分钟实现的东西不算差异化。**

**4. 输入条件对两组并不完全对称，这是有意为之但必须说明。**
Drain3 拿到的是 Loghub 标注里的 `Content` 字段（时间戳/主机/级别已被剥离），
本项目拿的是**原始日志**，必须自己解析。真实用户就是这样用的（指着日志文件点一下），
所以这是现实世界的公平对照；但它意味着本项目的成绩里包含了「格式覆盖能力」，
而 Drain3 的成绩里不包含。**换句话说：这一轮我们赢在工程完整性，不在算法。**

**5. 默认级别模式在无级别字段的日志上很糟**（HealthApp 1.9%、Zookeeper 2.2%、
OpenStack 10.4%）。这些系统把级别写在非标准位置，工具判不准。这是当前最该修的
已知缺陷 —— 语义上没错（那些行本就不是错误），但对用户是灾难：指着日志点一下，
拿到一份几乎空的报告且没有任何解释。

## 根因判定评测（CONFIRMED 档的精确率 / 召回率）

（CONFIRMED / LIKELY / INSUFFICIENT）无关。本节单独验证后者。

| Linux | 0※ | 0 |
| Zookeeper | 0 | 0 |
| Mac | 0 | 0 |
| HealthApp | 0 | 0 |

| OpenSSH | 0 | 0 |
| **合计** | **0** | **0** |

※ 正则只命中 1 行，且已核对为**误报**：

```
Oct 23 12:39:46 combo rsyncd[22517]: rsync error: error in rsync protocol data stream (code 12) at io.c(342)
```

`at io.c(` 撞上了 `at [\w$.]+\(` 这个模式 —— 它是 rsync 的错误信息，不是堆栈帧。
**写下来是因为「1 行 vs 0 行」差一个结论**：不核对就得写成「有 1 行堆栈」，
那会让「一行堆栈都没碰到过」这句话变成假的。

**全是单行日志格式。** 这意味着本文的保留率对照与「自信错误率 0%」
**一行堆栈解析代码都没有碰到过** —— 多行聚合、堆栈降噪、Caused-by 链
抽取这几条路径，全部只由单元测试和 `examples/sample_system.log`
（7 个堆栈帧 + 1 条 Caused-by）覆盖。

结论：**这套基准能验证「不丢事件类型」和「不乱下确定性结论」，
验证不了「堆栈处理得对不对」。** 后者需要含真实异常栈的数据集。
Loghub 2.0 的 14 个数据集里没有任何一个含异常栈 —— 这不是取样问题。

### 地面真相怎么来的

Loghub-2.0 标注的是日志模板、不是故障根因，所以本文第一版**完全没有验证
根因判定**。补救办法是绕开 Loghub：

`core/analysis.py` 里 CONFIRMED 的判据本身是**客观**的 —— 条目内有没有
`Caused by:` 链。于是可以**完全独立于本项目**、直接扫原始日志构造地面
真相，再与工具输出对账（`scripts/eval_rootcause.py`）。

Java 语义下链的方向：

```
java.lang.RuntimeException: query failed       <- 外层：症状
Caused by: java.sql.SQLTimeoutException: ...   <- 内层：因
Caused by: java.lang.OutOfMemoryError: ...    <- 最内层：根因
```

- **精确率（不乱说）** = 标为 CONFIRMED 且其引用行区间内确有 `Caused by` 的簇 / 全部 CONFIRMED 簇
- **自信错误率** = 1 − 精确率 ← 最该压到 0 的那个数
- **召回率（该说时说）** = 被正确认领的链 / 原始日志中真实存在的链

### 召回率有三个口径，差别必须写清楚（v2.7.0 口径重写）

| 口径 | 判据 | 强度 |
|---|---|---|
| **报告口径（对外只认这个）** | 覆盖该链的 CONFIRMED 簇，其**对外报告的根因文本**（`root_cause_reason` + 全部内层因变体）点名了该链的根因类名 | 答的是「用户照着报告能不能查到这一条」 |
| 簇文本 | 同上，但查的是簇的**样例原文**里有没有出现过这个类名 | 文本里有过 ≠ 工具把它说了出来 |
| 宽松 | 只要求该链的最内层行被任意 CONFIRMED 簇的行区间盖住 | 只证明位置对得上 |

**v2.7.0 为什么把对外口径换成「报告口径」**：旧口径查的是**样例原文**，
而一个簇的样例恰好是 `SocketException` 时，后面 29 次同类的链全被算作"被点名"
——可报告里根因那一行写的是另一个类。**用户照着报告查，报告里没有。**

更要紧的是：旧口径**检测不出 v2.6.0 那个缺陷**。「一簇只报一因」时变体不存在，
簇文本口径照样满分。**指标看不见自己该管的缺陷，比指标偏低更危险。**

顺手还修了评测脚本自身一个 bug：`_cluster_text` 读的是 `entry.stack_lines`，
而模型字段叫 `entry.stack`。属性名写错 → `getattr(..., None) or []` 静默返回空列表
→ 这个口径**从来没看过堆栈**，而 `Caused by` 全在堆栈里。指标不报错、不告警，
只是安静地退化。

**根因有两处，都在格式盲区**：

1. `generic` 规则没有 logcat 模式。Android 行是

   （实测 `E PushLog2824:` 被猜成 INFO）。
2. `Caused by` 的两条正则都锚在行首 `^`。而 Android 把整个异常压在一行里：

   ```
   12-17 19:42:44.457  3168  3307 E PushLog2824: com.x.PushException: boom  Caused by: java.net.SocketException: abort
   ```

   链**整条看不见**，工具只能判 `INSUFFICIENT`。它没有瞎猜，立场是对的——
   但从可用性看就是零。

**修法与收紧**：新增 `android_logcat` 模式（放在 patterns 首位）；`Caused by`
同时认行首（多行堆栈）与行内（单行异常）两种形态，**收紧点是行内 `Caused by:`
之后必须紧跟一个异常类名**（`Exception/Error/Throwable/Fault` 结尾），所以
`caused by: user input` 这种普通抱怨不会被抬成 CONFIRMED。
`tests/test_logcat.py` 13 条测试锁住行为，其中 3 条专门防误伤。

**这次 Android 的两个口径都是 100%，且不是宽松判据的假象**——严格口径要求簇
点名根因类名，Android 的 **8 个**不同根因类（NoExtAPIException / SocketException /
GaiException / ErrnoException / ConnectException / ClassNotFoundException /
JsonSyntaxException / IndexOutOfBoundsException）都被 10 个 CONFIRMED 簇点到了名。

`Caused by:`）。修法是先剥掉行首日志前缀再走同一套逻辑。**第三次了**——
地面真相自己失真，评测数字就全是错的。

### 这次评测抓到一个真 bug

第一版实现在 Zookeeper 上给出**自信错误率 100%** —— 一条
`INFO request started id=1` 被判成了确定性根因。根因：

```python
if any(_CAUSED_BY_RE.match(line) for line in stack):
    prior = _nearest_prior(ordered, c)   # 时间上最近的前一个错误簇
    caused_by_src.add(id(prior))         # 把「前一个」当成因
```

然后标 `CONFIRMED`，注释写着「因果方向由解析器确定，不是靠统计猜出来的」
—— **但时间相邻恰恰就是统计猜测**。真正的因果证据（同一条目堆栈里
`Caused by:` 指向的最内层异常）压根没被用上。

已改为：CONFIRMED **只**给携带 `Caused by:` 链的那一条目，reason 里点名
链上最内层的异常；跨簇时间相邻的边保留但降级为 LIKELY。修复后同一份日志：

```
[1] ERROR conf=CONFIRMED  根因：java.lang.OutOfMemoryError: Java heap space
[0] INFO  conf=LIKELY      因果链源头（2 个错误由其衍生）
```

注意根因从外层的 `RuntimeException: query failed`（**症状**）纠正成了
`OutOfMemoryError: Java heap space`（**真正的因**）。

**这个 bug 在 91% 覆盖率、三矩阵 CI 全绿、5 胜 0 负的状态下存在了整整一天，
是靠独立构造地面真相对账才发现的 —— 不是靠覆盖率。**

- **只有一个含链真实数据集，且样本量不大。** 131 条链 / 8 个根因类，

- **召回率的口径偏宽。** 行区间对账下，单簇覆盖的重复错误链都算被认领，

  这正是本项目同时给出严格口径（要求簇点名根因类名）的原因，

  正确弃权）。场景自建、非生产日志，不构成真实数据上的准确率证据。
- 「Caused by 链存在」被当作「因果方向确定」的充分条件。这在 Java /
  Python 异常语义下成立，但对**跨服务的分布式因果**不成立 —— 本工具
  不声称覆盖那种场景。

## 同预算公平对照：谁把根因证据留在了输出里？

同一份「根因埋在厚噪音里」的日志、同一个 token 预算，四种方法各显其能，
看谁的输出里还看得见因果链最内层的根因异常（留存判定**从宽**：异常类名或
消息前缀命中即算，不冤枉对照组）。

**语料（半合成，诚实标注）**：真实底座 = Loghub Hadoop 全量日志均匀采样
2,000 行（真实生产集群日志）；已知故障 = 复现语料的 5 条因果链均匀埋入。
地面真相仍由 `scan_chains` 独立扫描产生。

**结果**（`python scripts/eval_budget.py`，2026-10-14）：

| 方法 | 200tok | 400tok | 800tok | 1600tok | 3200tok | 6400tok |
| --- | --- | --- | --- | --- | --- | --- |
| tail -N（截最后 N 行） | 0% | 0% | 0% | 0% | 0% | 0% |
| grep 关键词 | 0% | 0% | 0% | 0~40% | 40% | 60% |
| Drain3（ICWS'17, 821★） | 0% | 0% | 0% | 0% | 40% | 100% |
| **log-ai-compressor** | 0% | 60% | **100%** | 100% | 100% | 100% |

（200tok 档全灭是诚实结果：预算小到连一份摘要都装不下时，谁都留不住证据；
噪声量 1,000 / 2,000 行两档复测趋势一致。tail 全程 0% 是因为故障埋在文件
中段，6,400tok 尚未够到 —— 正是「只看最后 N 行」的结构性盲区。）

**本表不含 LogSieve / LLM 摘要器**：离线环境拿不到 LogSieve 的实现与 LLM
API。评测框架的接口已留好（输入行列表 + 预算 → 输出文本），网络恢复后
可直接补测同一张表，无需改口径。

**基线是"朴素第一手动作"，不是各自的最优用法 —— 这条限制必须写明**：
- `grep` 基线**不带 `-A` 上下文行**，且撞满预算即停。真实排障里
  `grep -A30 'Caused by:'` 能拿到嵌套异常细节，表现会明显好于本表。
  本表测的是"先撒关键词"这一步的固有盲区，不是 grep 的能力上限。
- `Drain3` 按**簇频次降序**输出，稀有但致命的根因模板排在后面，小预算下
  必然被截掉 —— 这是"按频次排序 ≠ 按重要性排序"的体现，对它的默认配置
  公平，对"改配置后能更好"不公平。
- `tail -N` 全程 0% 是因为故障均匀埋在中段，结构上够不到，属实。

一句话：**这张表证明的是"同样预算下谁先失明"，不是"谁的能力上限更高"。**

## 本文不能证明什么

写清楚边界，避免过度解读：

- **本文的「证据保留率」不涉及根因判定。** Loghub-2.0 的标注是"日志模板"，
  不是"故障根因"。保留率衡量的是**事件类型是否还在**。根因置信三档由
  上一节单独评测：不乱说一侧（负例）由 Loghub 五数据集守住，正确认领一侧
  只用 **1 个**真实数据集测过 —— Android_v1 全量（报告口径 100%），
  精确率 100%、自信错误率 0%。样本小，见上。
- **Drain3 的保留率有测量偏袒**：它的输出是模板而非原始行，没有 LineId 可查，
  只能与标注模板做归一化模糊匹配（阈值 0.8）。这一项对 Drain3 略偏宽松，
  但也可能误判。
- **实测覆盖 10 / 14 个数据集**（v2.9.2 补齐 Linux / Mac / HPC / OpenSSH 后）。
  未覆盖的 5 个里，BGL / Spark / HDFS / Thunderbird 是 888 MB 的巨无霸、
  Hadoop 只做根因地面真相。**换网络限制曾让覆盖面卡在 5 个长达两个版本** ——
  v2.8.1 时本机 zenodo.org 域名级不可达（Python urllib / PowerShell / curl 三条
  路径分别得到 Connection reset / 超时 / Recv failure，而同环境 github、pypi 正常）。
  v2.9.2 环境恢复后一次补齐，**结论从「5 个全部领先」变成「9 个 7 胜 2 负」** ——
  这个代价正是覆盖面变宽要付的。
- **单次运行**，无重复实验、无显著性检验。
