# Loghub 2.0 公开基准：压缩比 vs 证据保留率

> 本文所有数字来自 `scripts/benchmark_loghub.py` 在 Loghub-2.0 真实日志上的实测，
> 可复现。**包括对我们不利的部分。**

## 要回答的问题

给定一份真实系统日志，在**同样的 token 预算**下，谁留住的「事件类型」最多？

行业里都在比**压缩比**（谁压得更小）。但压缩比是个会骗人的指标：
一个工具完全可以输出 50 万 token 的"压缩结果"并宣称压缩了 9 倍 ——
而 50 万 token 对 LLM 上下文来说毫无意义。所以这里同时报两个指标：

- **压缩比** = 原始日志 tokens / 输出 tokens
- **证据保留率** = 输出中仍可识别的人工标注事件类型数 / 事件类型总数

## 数据来源

- **数据集**：Loghub-2.0（[zenodo.org/record/8275861](https://zenodo.org/record/8275861)），
  ISSTA'24 "A Large-scale Evaluation for Log Parsing Techniques" 配套数据。
- **标注依据**：该数据集的 event template 是**人工标注**的（论文就是拿它当
  ground truth 评估 15 个解析器），不是任何工具的输出。所以"证据保留率"
  有真实标注依据。
- **本文覆盖**：**10 / 14** 个数据集。v2.9.2 之前是 5 个（按体积从小到大选取，
  212,394 行 / 25.3 MB 为上限）；那一版的限制其实是**网络**不是体积 ——

## 对照组

| 方法 | 说明 |
|---|---|
| `tail -N` | 最朴素：日志太大，只看最后 N 行 |
| `grep` | 关键词过滤 `error\|exception\|fail\|fatal\|...` |
| **Drain3** | 学术标准日志模板抽取（ICWS'17，821★）。喂给它 Loghub 自己标注的 `Content` 字段（已剥离时间戳/主机/级别），这是 Drain 官方文档明确要求的输入形态 |
| **log-ai-compressor** | 本项目。跑两种模式：默认级别（ERROR/FAIL 排障）与全级别（摘要） |

**公平性说明**：第一版基准把带时间戳的原始行直接喂给 Drain3，导致它只拿到
63.6%（Proxifier）；按其文档要求改喂 `Content` 字段后升到 72.7%。
**这个修正让对照组变强，最终表格用的是修正后的数字。**

## 结果一：证据保留率

**先说清楚 v2.9.5 撤回了这张表的上一版。** 当时的覆盖率在数**报告里根本没出现
的簇**（详见下方「v2.9.5 撤回经过」）。下面是修正口径后的重测：

| 数据集 | 标注事件 | 本项目(交付 top20) | **本项目(同预算 32k)** | 本项目(全量) | Drain3 | **LogsLop** | tail @32k | grep @32k |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Proxifier | 11 | 81.8% | **100.0%** | 100.0% | 72.7% | **27.3%** | 63.6% | 45.5% |
| Apache | 29 | 55.2% | **100.0%** | 100.0% | 93.1% | **44.8%** | 27.6% | 34.5% |
| OpenSSH | 38 | 36.8% | **92.1%** | 92.1% | 92.1% | **34.2%** | 55.3% | 26.3% |
| Hadoop | 236 | 8.5% | **91.1%** | 91.1% | 80.5% | **13.1%** | 32.6% | 13.1% |
| Zookeeper | 89 | 22.5% | **92.1%** | 92.1% | 76.4% | **23.6%** | 79.8% | 9.0% |
| Linux | 338 | 2.4% | **90.8%** | 90.8% | 66.6% | **55.6%** | 3.6% | 3.6% |
| HealthApp | 156 | 11.5% | **89.7%** | 89.7% | 83.3% | **7.1%** | 32.1% | 3.8% |
| Mac | 626 | 3.2% | **58.5%** | 91.5% | **72.2%** | **16.1%** | 24.8% | 5.1% |
| HPC | 74 | 23.0% | **85.1%** | 85.1% | **87.8%** | **4.1%** | 1.4% | 4.1% |
| OpenStack | 48 | 37.5% | **52.1%** | 52.1% | 41.7% | **18.8%** | 20.8% | 8.3% |

**三个口径，三个不同的问题：**

| 口径 | 报告里给几个簇 | 对 Drain3 |
|---|---|---|
| **交付口径 top20** | 产品默认 `top_n=20`，用户开箱即用**真拿到手**的 | **1 胜 9 负** |
| **同预算 32k**（主指标） | 32k token 预算内尽量多放，和 Drain3 花一样的钱 | **7 胜 1 平 2 负** |
| **全量口径** | 全部簇 —— **用户拿不到这么多**，是聚类质量上界 | 8 胜 1 平 1 负 |

**为什么交付口径那么难看**：Mac 有 626 种标注事件、Linux 有 338 种，
而产品默认只给 20 个簇 —— **20 个簇在物理上就装不下 626 种事件**。
这一列低不是工具差，是产品决策与这个指标的**结构性冲突**，v2.9.5 已写明。

**胜负怎么判的**：一律按**事件种数**比，不比四舍五入后的百分数。
报告只有 1 位小数，0.05pp 以内的差**与舍入误差分不开**，落在容差里一律记平。
（v2.9.6 之前是直接比百分数，把 OpenSSH 一个 0.005pp 的舍入差判成了「胜」——
两边其实都是 35/38。）

> 上一版这里还有一列「本项目(默认级别, 排障)」，本版**不再列出**：
> 那 10 个数是带着 v2.9.5 已撤回的覆盖率 bug 测的。现在要它请跑
> `python scripts/benchmark_loghub.py`，那一行还在输出里。

上一版写的是「5 个数据集全部第一」。那句话当时是真的，但那 5 个是
**在能连上 zenodo 的环境里挑的**，挑不出「会输」的那几个。补测之后结论变了，
这正是把覆盖面从 5 扩到 10 的代价与价值：**数字变难看了，可信度变高了。**

### v2.9.5 撤回经过：指标在数用户没收到的东西

上一版这张表写的是「严格档 10 胜 0 平 0 负」。**该结论已撤回**，理由如下 ——
这一节保留原文与数字，不修饰，因为**撤回过程本身就是这个项目的一部分**。

**病根是 `top_n: 0` 不等于「不限簇数」。** 两处错叠在一起：

1. 调用方传 `top_n: 0`，而 pipeline 里是
   `top_n = top_n if top_n else FilterConfig.defaults().top_n` ——
   **0 是 falsy，回落到 `DEFAULT_TOP_N = 20`**。「不限簇数」从来没生效过。
2. 覆盖率却按 `result.clusters` **全部**统计。

于是**指标和它描述的文本是两个不同的对象**：

| | 覆盖率数的是 | 报告里显示的是 |
|---|---|---|
| 默认档 | 全部 93 个簇 | 只有 20 个 |
| 「严格档」 | 全部 **1,831** 个簇 | 只有 20 个 |

实测：OpenSSH 在所谓严格档下切出 **1,831 个簇 / 38 种事件（每种 48 个簇）**，
覆盖率因此报到 100% —— 而报告只有 **809 个 token，装不下 1,831 行**。
**那不是保住证据，那是把证据堆在内存里。**

**同类 bug 在同一个仓库里出现过三次，形状完全一样：**

| 版本 | 错 | 共同形状 |
|---|---|---|
| v2.9.2 | `discover()` 只扫一个根目录，fetch 解到另一个 | 断链的一端没人发现 |
| v2.9.3 | `ALL_LEVELS` 手写，漏 `FAIL`、收三个死别名 | **让数字朝好看的方向偏** |
| v2.9.5 | `top_n=0` 被当 falsy，覆盖率按全量统计 | **让数字朝好看的方向偏** |
| v2.9.6 | 拿四舍五入的百分数判胜负 | **让平手显示成赢** |

四次都是「**一个对外数字，没有任何东西在校它**」。修法不是改措辞，是加门禁：
覆盖率 ≤ 实际展示的簇数、全量口径 ⊇ 交付口径、`ALL_LEVELS` 等于规范词表、
胜负按计数比。

### 两处落后及其病因（v2.9.6 更新）

先更正 v2.9.2 的一处**误判**：当时把 OpenSSH 写成「过度合并」，实测是错的 ——
那 11 个未覆盖事件里有 10 个的行数**根本没进簇**（约 43 万行，占 68%），
不是被合并，是被 `ALL_LEVELS` 漏掉的 `FAIL` 档整批丢弃。真因在测量工具，
修掉之后 OpenSSH 从 71.1% 变成 **92.1%，与 Drain3 打平**（不是赢）。

**同预算档剩下的两个负例，病因不同，不是一回事：**

**① HPC 85.1% vs Drain3 87.8% —— 簇粒度比标注粗**

76 个簇 / 74 种事件 / 覆盖 63（85.1%）。未覆盖的 11 种里，大头是
**极短通用消息**：

| 事件 | 行数 | 样例 |
|---|---:|---|
| E57 | 13,414 | `boot (command 1894)` |
| E72 | 2,257 | `Link ok` |
| E49 | 268 | `risBoot (command 1899)` |
| E44 | 355 | `power/control problem` |
| E64 | 148 | `starting` |

`action start ... wait` 与 `action start ... boot` 只差一个词，在 0.85 阈值下被合并；
而 Loghub 标注把它们算两类事件 —— **簇粒度比标注粗时事件就"看不见"了**。

**② Mac 58.5% vs Drain3 72.2% —— 每 token 效率，不是丢事件**

我们 30,566 token 换 58.5%，Drain3 18,930 token 换 72.2%。
但**全量口径我们 91.5% 是赢的** —— 说明聚类本身没丢事件，是**报告装得太满**。
修法是压报告密度（让同样 token 装下更多事件），不是调阈值。

**调相似度阈值能把 HPC 凑成「全胜」，本项目明确不做那种事** ——
对着基准调参得到的领先不是领先。短消息需要独立处理，是下一步该单独设计的
工程问题。

#### LogsLop：加进来的那个正面竞品（v2.5.0）

[LogsLop](https://github.com/amd/logslop) 是 AMD 在 2026-07 的 ROCm 博客里开源的日志去重工具
（`pip install logslop`，零依赖），也是**目前最接近的正面竞品** —— 它同样用 Loghub
和 Drain3 做对照，并提出了 SURCL 指标。v2.5.0 把它纳入对照，因为它承认自己
在 PA 上不敌 Drain3（81% vs 99.75%），是个诚实但目标不同的工具。

对照口径对它公平：喂**原始日志行**（这是它自己文档与博客里的标准用法；
Drain 要剥离结构化头是因为它的模板抽取需要，对照时给各自应得的输入才公平）。
它保留的也是原始行，所以能按 LineId 精确回查，映射口径与 tail / grep / 本项目一致，
不存在 Drain3 那种「模板相似度」误判余地。标注覆盖率实测 **100%**（每个数据集
每一行都有 EventId），所以也不是标注稀疏导致的低估。

**结论：去重工具优化的目标（别让我看两遍一样的东西）与证据保留的目标
（别弄丢我的根因证据）方向相反。** LogsLop 会把文本相似的不同事件合并掉，
所以它在全部 9 个数据集上都低于 Drain3，且**几乎不随预算增长**：

| 数据集 | @500tok | @1k | @4k | @32k |
|---|---:|---:|---:|---:|
| Apache（LogsLop） | 37.9% | 44.8% | 44.8% | **44.8%** |
| Apache（本项目） | **100.0%** | **100.0%** | **100.0%** | **100.0%** |
| Zookeeper（LogsLop） | 15.7% | 21.3% | 23.6% | **23.6%** |
| Zookeeper（本项目） | **92.1%** | **92.1%** | **92.1%** | **92.1%** |

给再多 token 它也救不回来被合并掉的事件；而本项目在最小预算档就已到顶。
耗时上本项目也占优：HealthApp 上本项目 15.19s，Drain3 607.58s（**40 倍**）。

**10 个数据集里，同预算档 7 胜 1 平 2 负**（HPC 与 Mac 输给 Drain3，
OpenSSH 打平，见「两处落后及其病因」）。交付口径 1 胜 9 负 —— 那个数字不是
算法变差，是产品只给 20 个簇而 Mac 有 626 种事件。

### 这两个数字是怎么来的（不是算法变强了）

第一轮实测我们是 **3 胜 2 负**（Zookeeper 71.9%、HealthApp 78.8%）。用
`scripts/diagnose_missed_events.py` 逐条追查丢失的事件后发现：

> **丢的不是「聚类合并」，是「根本没解析出来」。**

ZooKeeper 用的是 `<时间戳> - <级别> [<模块>] - <内容>`，但 `generic` 规则集里
`iso_level_module` 的级别前只允许 `[` 或 `(`，不接受 `-`，于是整份日志掉进无结构
兜底：message 里保留完整时间戳、module 为空、指纹噪声大、不同事件被并簇。

HealthApp 用的是 `20171223-22:15:29:606|模块|用户ID|内容`，**非 ISO 紧凑时间戳 +
管道分隔**，同样无模式匹配 —— 时间戳解析为 `None`，**整份日志的时间直方图是空的**。

补了两条规则后（`iso_dash_level_module` / `pipe_delimited_device`）：

| 数据集 | 修复前 | 修复后 | 增量 |
|---|---:|---:|---:|
| Zookeeper | 71.9% | 92.1% | **+20.2** |
| HealthApp | 78.8% | 87.8% | **+9.0** |

**结论要老实说：这不是算法进步，是补格式覆盖的洞。** 聚类本身仍是
`difflib` 编辑距离 + 级别桶回退，没有 Drain 的前缀树和模板在线精修。
在**解析正常**的日志上（Apache / ProxIFIER 那种标准格式），我们领先的原因是
保留了每簇的原始样例行，而 Drain 只吐模板 —— 不是因为我们分得更准。

另外注意 **默认级别模式下 Zookeeper 从 11.2% 降到 2.2%**：这是**变准了**而非变差。
修复前那些行靠「消息里含 error/fail 关键词」被误捞进错误集，实际上它们是
`INFO` 级的启动日志。修复后级别被正确识别为 INFO，于是被正确排除。

## 结果二：输出规模

### 口径与复测（2026-10-14，统一数字的唯一出处）

**先说清楚：本节所有数字只认这一张表。** 此前本文件与 README 各有一张
"brief_summary 输出规模"表，数字互相矛盾（710/562/266/453/512 与
743/548/470/499/746），分别出自两个不同版本的代码与估算器跑分，从未
对齐过。现在统一按下面两种口径重测（`estimate_tokens` 估算）：

- **对照口径**（同预算对照用）：`top_n=0, context_lines=0`，即
  benchmark 里给所有方法的同预算条件；
- **CLI 默认口径**（人读取证报告）：`context_lines=50`、`top_n` 默认。

| 数据集 | 原始 tokens | summary（对照口径·默认级别/全级别） | summary（CLI 口径·全级别） | md（CLI 默认） | text | json |
|---|---:|---:|---:|---:|---:|---:|
| Apache | 1,243,921 | 578 / 564 | 564 | 47,962 | 50,357 | 43,561 |
| Zookeeper | 2,582,577 | 313 / 517 | 517 | 80,412 | 82,906 | 73,774 |
| Hadoop | 7,971,821 | 788 / 708 | 708 | 94,448 | 97,090 | 15,214 |
| Proxifier / HealthApp / OpenStack | — | **未复测** | — | — | — | — |

（Proxifier / HealthApp / OpenStack 托管在 zenodo，本机网络不可达，
拿不到数据就不填 —— 历史数字见下方"首轮对照"，已降级为趋势参考。）

- `summary`（投喂 LLM 口径）：**313–788 tokens**，日志从 12 万行涨到 18 万行
  （原始 1.2M → 8.0M tokens，6.4 倍），输出仍在数百 token 量级 ——
  **有上界、不随日志规模增长**，但不是恒定值，跨度约 2.5 倍（取决于簇数）。
- `md` / `text`（人读的完整报告，context=50）：**4.8 万–9.7 万 tokens**，
  取决于有多少簇、多少实例需要展开。它仍远小于原文（压缩 28x–85x），
  但**不是恒定**，也绝不该拿它去对标「几百 token」。
- 复现命令：对 `data/loghub/<name>_full.log` 跑
  `service.analyze(..., params={"levels": ALL, "context_lines": 50})`
  再 `estimate_tokens(service.export_text(result, fmt))`。

**修掉的两处旧表述**：① 旧文写「266–710 tokens，跨度 1.06 倍」——
266→710 是 2.67 倍，算术就错了；② 「输出恒定在 470–746 tokens」——
那既不是恒定（跨度 1.59 倍），也无法在当前代码上复现。正确说法是
「**有上界、与日志规模无关**」。

### 修复记录：实例行号曾把报告撑到 27 万字符

修复前，OpenStack 上 3 个簇的 md 报告是 **519 行 / 272,744 字符（≈68k tokens）**，
其中**单行 16,828 字符** —— 一个簇的 2000 个实例行号被平铺进一行。

改成摘要式呈现后：同场景 **41,723 字符（-85%）**，最长行 361 字符。
`tests/test_report_size.py` 把体积钉成硬约束。

### 与 Drain3 对比（首轮对照，趋势结论仍有效）

**口径警告**：下表是**首轮**跑分，运行于更早的代码与 token 估算器，
绝对值无法在当前版本复现（当前值以上表为准）。保留它只为趋势结论：
「Drain3 的输出随模板/参数数爆炸，本项目有上界」——这个形状不会因
版本漂移改变。

| 数据集 | 原始 tokens（旧口径） | 本项目输出（旧口径） | Drain3 输出 |
|---|---:|---:|---:|
| Proxifier | 624,518 | 743 | 317 |
| Apache | 1,230,926 | 548 | 431 |
| Zookeeper | 2,564,008 | 470 | 980 |
| OpenStack | 15,299,983 | **746** | **73,569** |
| HealthApp | 5,067,779 | **499** | **566,802** |

趋势结论（不受绝对值漂移影响）：本项目输出**有上界**（首轮 470–746、
本轮复测 313–788，都是数百 token），Drain3 从 317 到 566,802（跨度 1789 倍）。

在最大的两个数据集上，Drain3 的"压缩结果"已经不可用：

- **HealthApp**：压缩比只有 **9x**，耗时 **578 秒**。一个 56 万 token 的压缩结果
  等于没压缩。
- **OpenStack**：压缩比 208x，输出 73,569 tokens。

原因：Drain3 的输出行数 ≈ 模板数 × 每模板的参数，模板一多参数就爆炸。
本项目的输出行数 ≈ 簇数，**且每簇只存一份样例，与出现次数无关**。

## 结果三：耗时

## 上下文行数对报告体积的影响（供选择默认值）

md 报告的体积几乎完全由 `--context` 决定（每个簇 2×N 行原始日志）。
实测 HealthApp（原始 5,120,878 tokens，全簇无 Top 限制）：

| `--context` | md 报告 | 行数 | tokens | 相对原文压缩 |
|---:|---:|---:|---:|---:|
| 0 | 4,589 字符 | 110 | 1,542 | 3,321x |
| 10 | 15,802 字符 | 250 | 4,362 | 1,174x |
| **50（当前默认）** | 56,396 字符 | 650 | 14,511 | 353x |

**默认仍是 50，且不建议改**：这是 R20 时的明确用户决策，50 行上下文对
**人读的取证报告**是合理的（要看出「什么导致了这一行」）。14.5k tokens
放不进 LLM 上下文，但投喂 LLM 的场景本来就不该用 md，而是用
`--format summary`（复测 313–788 tokens，见「结果二」统一口径表）。

若要更短的报告：`--context 10` 可压到 4.4k tokens，语义信息基本不丢。

## 结论（诚实版）

**1. 证据保留率（同预算 32k）10 个数据集里 7 胜 1 平 2 负 —— 而那些胜里的领先是"补洞"补出来的，不是算法更强。**
真正的算法差距仍然存在：我们的聚类没有前缀树剪枝、没有模板在线精修。
在**解析正常**的日志上领先，是因为我们为每簇保留了一行原始样例作为可引用证据，
而 Drain 只吐模板 —— 样本行天然覆盖更多事件类型，但这不等于「分得更准」。
交付口径 1 胜 9 负、全量口径 8 胜 1 平 1 负，三个都报，见结果一。

**1b. 剩下的落后写明了病因**（HPC：极短通用消息被并簇），不是「随机波动」——
**一个能被解释的失败，比一个无法解释的成功更有用**，但那前提是它被写在明处。

**2. 我们赢在"输出规模有上界"。** 无论日志是 2 万行还是 21 万行、11 种还是
156 种事件类型，summary 输出都在数百 token（复测 313–788）。这直接决定了
它能不能塞进 LLM 上下文。

**3. 这仍然是一条工程性质，不是护城河。** 给 Drain3 加一个 `--max-clusters`
十分钟就能做到。**能被十分钟实现的东西不算差异化。**

**4. 输入条件对两组并不完全对称，这是有意为之但必须说明。**
Drain3 拿到的是 Loghub 标注里的 `Content` 字段（时间戳/主机/级别已被剥离），
本项目拿的是**原始日志**，必须自己解析。真实用户就是这样用的（指着日志文件点一下），
所以这是现实世界的公平对照；但它意味着本项目的成绩里包含了「格式覆盖能力」，
而 Drain3 的成绩里不包含。**换句话说：这一轮我们赢在工程完整性，不在算法。**

**5. 默认级别模式在无级别字段的日志上很糟**（HealthApp 1.9%、Zookeeper 2.2%、
OpenStack 10.4%）。这些系统把级别写在非标准位置，工具判不准。这是当前最该修的
已知缺陷 —— 语义上没错（那些行本就不是错误），但对用户是灾难：指着日志点一下，
拿到一份几乎空的报告且没有任何解释。

## 根因判定评测（CONFIRMED 档的精确率 / 召回率）

本文上面的「证据保留率」衡量的是**事件类型还在不在**，与本项目的置信三档
（CONFIRMED / LIKELY / INSUFFICIENT）无关。本节单独验证后者。

### 一个必须说清的前提：这 10 个数据集里没有一行真堆栈

逐文件扫过原始日志，统计堆栈帧（`at com.foo.Bar(` / `File "x.py", line N` /
`#N 0x... in ...` / `Traceback`）与 `Caused by`（**v2.9.2 重扫，覆盖 1,760,767 行**）：

| 数据集 | 原始堆栈帧 | `Caused by` |
|---|---:|---:|
| Proxifier | 0 | 0 |
| Apache | 0 | 0 |
| Linux | 0※ | 0 |
| Zookeeper | 0 | 0 |
| Mac | 0 | 0 |
| HealthApp | 0 | 0 |
| OpenStack | 0 | 0 |
| HPC | 0 | 0 |
| OpenSSH | 0 | 0 |
| **合计** | **0** | **0** |

※ 正则只命中 1 行，且已核对为**误报**：

```
Oct 23 12:39:46 combo rsyncd[22517]: rsync error: error in rsync protocol data stream (code 12) at io.c(342)
```

`at io.c(` 撞上了 `at [\w$.]+\(` 这个模式 —— 它是 rsync 的错误信息，不是堆栈帧。
**写下来是因为「1 行 vs 0 行」差一个结论**：不核对就得写成「有 1 行堆栈」，
那会让「一行堆栈都没碰到过」这句话变成假的。

**全是单行日志格式。** 这意味着本文的保留率对照与「自信错误率 0%」
**一行堆栈解析代码都没有碰到过** —— 多行聚合、堆栈降噪、Caused-by 链
抽取这几条路径，全部只由单元测试和 `examples/sample_system.log`
（7 个堆栈帧 + 1 条 Caused-by）覆盖。

结论：**这套基准能验证「不丢事件类型」和「不乱下确定性结论」，
验证不了「堆栈处理得对不对」。** 后者需要含真实异常栈的数据集。
Loghub 2.0 的 14 个数据集里没有任何一个含异常栈 —— 这不是取样问题。

### 地面真相怎么来的

Loghub-2.0 标注的是日志模板、不是故障根因，所以本文第一版**完全没有验证
根因判定**。补救办法是绕开 Loghub：

`core/analysis.py` 里 CONFIRMED 的判据本身是**客观**的 —— 条目内有没有
`Caused by:` 链。于是可以**完全独立于本项目**、直接扫原始日志构造地面
真相，再与工具输出对账（`scripts/eval_rootcause.py`）。

Java 语义下链的方向：

```
java.lang.RuntimeException: query failed       <- 外层：症状
Caused by: java.sql.SQLTimeoutException: ...   <- 内层：因
Caused by: java.lang.OutOfMemoryError: ...    <- 最内层：根因
```

- **精确率（不乱说）** = 标为 CONFIRMED 且其引用行区间内确有 `Caused by` 的簇 / 全部 CONFIRMED 簇
- **自信错误率** = 1 − 精确率 ← 最该压到 0 的那个数
- **召回率（该说时说）** = 被正确认领的链 / 原始日志中真实存在的链

### 结果

| 数据集 | 行数 | 真实因果链 | CONFIRMED | 精确率 | **自信错误率** | 召回率 |
|---|---:|---:|---:|---:|---:|---:|
| Zookeeper | 74,273 | **0** | **0** | — | **0%** | — |
| 其余 4 个数据集 | 455,324 | 0 | 0 | — | 0% | — |

**零因果链时零确定性断言。** 20 个簇被标为根因（全是 LIKELY），63 个
INSUFFICIENT，整体判定 `LIKELY`、`can_conclude: False`。

### 复现语料结果（功能基准，非生产日志）

真实数据集拿不到含栈日志期间，把「精确率/召回率」的**机制**固化成可复跑的
复现语料（`scripts/eval_rootcause.py --repro`）：自建故障场景 + 真实 Java
异常类/栈帧/日志格式（logback 输出形态，含 `HikariPool$1` 这类匿名类异常、
3 层深链、无链对照组）。地面真相仍由 `scan_chains` 独立扫描产生：

| 场景 | 行数 | 真实因果链 | CONFIRMED | 精确率 | **自信错误率** | 召回率 |
|---|---:|---:|---:|---:|---:|---:|
| order_service（双链，3 层 + 2 层） | 24 | 2 | 2 | 100% | **0%** | 100% |

**口径**：这是功能基准 —— 验证指标机制能抓住回归（例如历史上那个把

**不构成真实生产数据上的准确率证据**。

**它第一跑就抓到评测器自己的两个 bug**（基准连评测器也照抓不误）：
地面真相扫描器只认 `*Exception/*Error/*Throwable` 结尾的类名，
`com.zaxxer.hikari.pool.HikariPool$1` 这类匿名类异常会让整条链消失

消息模板不含栈 —— 召回率因此整体假 0%。两个都已修，均以行区间对账为准。

### 召回率有三个口径，差别必须写清楚（v2.7.0 口径重写）

| 口径 | 判据 | 强度 |
|---|---|---|
| **报告口径（对外只认这个）** | 覆盖该链的 CONFIRMED 簇，其**对外报告的根因文本**（`root_cause_reason` + 全部内层因变体）点名了该链的根因类名 | 答的是「用户照着报告能不能查到这一条」 |
| 簇文本 | 同上，但查的是簇的**样例原文**里有没有出现过这个类名 | 文本里有过 ≠ 工具把它说了出来 |
| 宽松 | 只要求该链的最内层行被任意 CONFIRMED 簇的行区间盖住 | 只证明位置对得上 |

**v2.7.0 为什么把对外口径换成「报告口径」**：旧口径查的是**样例原文**，
而一个簇的样例恰好是 `SocketException` 时，后面 29 次同类的链全被算作"被点名"
——可报告里根因那一行写的是另一个类。**用户照着报告查，报告里没有。**

更要紧的是：旧口径**检测不出 v2.6.0 那个缺陷**。「一簇只报一因」时变体不存在，
簇文本口径照样满分。**指标看不见自己该管的缺陷，比指标偏低更危险。**

顺手还修了评测脚本自身一个 bug：`_cluster_text` 读的是 `entry.stack_lines`，
而模型字段叫 `entry.stack`。属性名写错 → `getattr(..., None) or []` 静默返回空列表
→ 这个口径**从来没看过堆栈**，而 `Caused by` 全在堆栈里。指标不报错、不告警，
只是安静地退化。

**这是本项目至今最值钱的一次实测**——不是因为数字好，而是因为 **0% 暴露了一个
真实的能力缺口**，而且它藏在"已经测过一个数据集"这个结论背后。

**根因有两处，都在格式盲区**：

1. `generic` 规则没有 logcat 模式。Android 行是
   `12-17 19:42:44.457  3168  3307 E PushLog2824: ...`——
   **无年份**（所有 `iso_*` 模式都要求 `\d{4}-`）、**级别是单字母**
   （`{LEVEL}` 展开的是词表，匹配不上）、时间戳与级别之间还夹着 PID/TID。
   结果整行落进无结构兜底：时间戳与模块全丢，级别靠关键词猜
   （实测 `E PushLog2824:` 被猜成 INFO）。
2. `Caused by` 的两条正则都锚在行首 `^`。而 Android 把整个异常压在一行里：

   ```
   12-17 19:42:44.457  3168  3307 E PushLog2824: com.x.PushException: boom  Caused by: java.net.SocketException: abort
   ```

   链**整条看不见**，工具只能判 `INSUFFICIENT`。它没有瞎猜，立场是对的——
   但从可用性看就是零。

**修法与收紧**：新增 `android_logcat` 模式（放在 patterns 首位）；`Caused by`
同时认行首（多行堆栈）与行内（单行异常）两种形态，**收紧点是行内 `Caused by:`
之后必须紧跟一个异常类名**（`Exception/Error/Throwable/Fault` 结尾），所以
`caused by: user input` 这种普通抱怨不会被抬成 CONFIRMED。
`tests/test_logcat.py` 13 条测试锁住行为，其中 3 条专门防误伤。

**这次 Android 的两个口径都是 100%，且不是宽松判据的假象**——严格口径要求簇
点名根因类名，Android 的 **8 个**不同根因类（NoExtAPIException / SocketException /
GaiException / ErrnoException / ConnectException / ClassNotFoundException /
JsonSyntaxException / IndexOutOfBoundsException）都被 10 个 CONFIRMED 簇点到了名。

**评测器自己也在这份数据上抓到一个 bug**（与上文同类）：`scan_chains` 同样因为
两条正则锚在行首，在 Android 上扫出 **0 条链**（文件里明明有 131 条真实
`Caused by:`）。修法是先剥掉行首日志前缀再走同一套逻辑。**第三次了**——
地面真相自己失真，评测数字就全是错的。

**评测器在真实数据上又抓到自己一个 bug**（与上文同类，必须记一笔）：
`scan_chains` 此前只认「裸异常摘要行」开头的链，而真实日志把异常摘要
**内嵌在带时间戳的日志行里**（`2015-10-19 ... INFO [...] Task: Communication
exception: java.io.IOException: ...`），导致整条链被漏扫 —— 工具正确的
Caused-by 判定反被对账判成"自信错误"（真实 Hadoop 上假报自信错误率 66%）。
改成用时间戳行作条目边界重建扫描后，复现语料口径不变（仍 5 链 100%/100%/0%），
真实数据转为精确率 100%、自信错误率 0%。**地面真相自己失真时，评测数字
全是错的** —— 这正是"独立构造地面真相对账"要反复做的原因。

### 这次评测抓到一个真 bug

第一版实现在 Zookeeper 上给出**自信错误率 100%** —— 一条
`INFO request started id=1` 被判成了确定性根因。根因：

```python
if any(_CAUSED_BY_RE.match(line) for line in stack):
    prior = _nearest_prior(ordered, c)   # 时间上最近的前一个错误簇
    caused_by_src.add(id(prior))         # 把「前一个」当成因
```

然后标 `CONFIRMED`，注释写着「因果方向由解析器确定，不是靠统计猜出来的」
—— **但时间相邻恰恰就是统计猜测**。真正的因果证据（同一条目堆栈里
`Caused by:` 指向的最内层异常）压根没被用上。

已改为：CONFIRMED **只**给携带 `Caused by:` 链的那一条目，reason 里点名
链上最内层的异常；跨簇时间相邻的边保留但降级为 LIKELY。修复后同一份日志：

```
[1] ERROR conf=CONFIRMED  根因：java.lang.OutOfMemoryError: Java heap space
[0] INFO  conf=LIKELY      因果链源头（2 个错误由其衍生）
```

注意根因从外层的 `RuntimeException: query failed`（**症状**）纠正成了
`OutOfMemoryError: Java heap space`（**真正的因**）。

**这个 bug 在 91% 覆盖率、三矩阵 CI 全绿、5 胜 0 负的状态下存在了整整一天，
是靠独立构造地面真相对账才发现的 —— 不是靠覆盖率。**

### 本文不能证明什么（根因部分）

- **真实数据集现在只剩一种日志形态。** Android_v1 全量（logcat 单行异常，
  131 条链 / 8 个根因类）。Hadoop 那组（容器日志、多层 Caused-by 栈）已随
  数据撤回而作废。其它日志形态（Python traceback、Go panic、
  Node unhandled rejection、Windows 事件日志…）**未测**，结论未必外推。
- ~~**Android 是切片测的。**~~ **v2.4.0 已跑全量**：1,555,005 行 / 131 条链，
  原始密度 1 / 11,870 行。结论未因密度回落而翻转（见上）。这条软肋已消除。
- **只有一个含链真实数据集，且样本量不大。** 131 条链 / 8 个根因类，
  「报告口径召回 100%」不能读作「在各种日志形态上都成立」。
- **召回率的口径偏宽。** 行区间对账下，单簇覆盖的重复错误链都算被认领，
  衡量的是"这类根因有没有被指出来"，不是"每条链都被单独点名" ——
  这正是本项目同时给出严格口径（要求簇点名根因类名）的原因，
  **对外只认严格口径**。
- **复现语料（`--repro`）只验证机制**（5 条链的正确认领 + 无链对照组的
  正确弃权）。场景自建、非生产日志，不构成真实数据上的准确率证据。
- 「Caused by 链存在」被当作「因果方向确定」的充分条件。这在 Java /
  Python 异常语义下成立，但对**跨服务的分布式因果**不成立 —— 本工具
  不声称覆盖那种场景。

## 同预算公平对照：谁把根因证据留在了输出里？

同一份「根因埋在厚噪音里」的日志、同一个 token 预算，四种方法各显其能，
看谁的输出里还看得见因果链最内层的根因异常（留存判定**从宽**：异常类名或
消息前缀命中即算，不冤枉对照组）。

**语料（半合成，诚实标注）**：真实底座 = Loghub Hadoop 全量日志均匀采样
2,000 行（真实生产集群日志）；已知故障 = 复现语料的 5 条因果链均匀埋入。
地面真相仍由 `scan_chains` 独立扫描产生。

**结果**（`python scripts/eval_budget.py`，2026-10-14）：

| 方法 | 200tok | 400tok | 800tok | 1600tok | 3200tok | 6400tok |
| --- | --- | --- | --- | --- | --- | --- |
| tail -N（截最后 N 行） | 0% | 0% | 0% | 0% | 0% | 0% |
| grep 关键词 | 0% | 0% | 0% | 0~40% | 40% | 60% |
| Drain3（ICWS'17, 821★） | 0% | 0% | 0% | 0% | 40% | 100% |
| **log-ai-compressor** | 0% | 60% | **100%** | 100% | 100% | 100% |

（200tok 档全灭是诚实结果：预算小到连一份摘要都装不下时，谁都留不住证据；
噪声量 1,000 / 2,000 行两档复测趋势一致。tail 全程 0% 是因为故障埋在文件
中段，6,400tok 尚未够到 —— 正是「只看最后 N 行」的结构性盲区。）

**本表不含 LogSieve / LLM 摘要器**：离线环境拿不到 LogSieve 的实现与 LLM
API。评测框架的接口已留好（输入行列表 + 预算 → 输出文本），网络恢复后
可直接补测同一张表，无需改口径。

**基线是"朴素第一手动作"，不是各自的最优用法 —— 这条限制必须写明**：
- `grep` 基线**不带 `-A` 上下文行**，且撞满预算即停。真实排障里
  `grep -A30 'Caused by:'` 能拿到嵌套异常细节，表现会明显好于本表。
  本表测的是"先撒关键词"这一步的固有盲区，不是 grep 的能力上限。
- `Drain3` 按**簇频次降序**输出，稀有但致命的根因模板排在后面，小预算下
  必然被截掉 —— 这是"按频次排序 ≠ 按重要性排序"的体现，对它的默认配置
  公平，对"改配置后能更好"不公平。
- `tail -N` 全程 0% 是因为故障均匀埋在中段，结构上够不到，属实。

一句话：**这张表证明的是"同样预算下谁先失明"，不是"谁的能力上限更高"。**

## 本文不能证明什么

写清楚边界，避免过度解读：

- **本文的「证据保留率」不涉及根因判定。** Loghub-2.0 的标注是"日志模板"，
  不是"故障根因"。保留率衡量的是**事件类型是否还在**。根因置信三档由
  上一节单独评测：不乱说一侧（负例）由 Loghub 五数据集守住，正确认领一侧
  只用 **1 个**真实数据集测过 —— Android_v1 全量（报告口径 100%），
  精确率 100%、自信错误率 0%。样本小，见上。
- **Drain3 的保留率有测量偏袒**：它的输出是模板而非原始行，没有 LineId 可查，
  只能与标注模板做归一化模糊匹配（阈值 0.8）。这一项对 Drain3 略偏宽松，
  但也可能误判。
- **实测覆盖 10 / 14 个数据集**（v2.9.2 补齐 Linux / Mac / HPC / OpenSSH 后）。
  未覆盖的 5 个里，BGL / Spark / HDFS / Thunderbird 是 888 MB 的巨无霸、
  Hadoop 只做根因地面真相。**换网络限制曾让覆盖面卡在 5 个长达两个版本** ——
  v2.8.1 时本机 zenodo.org 域名级不可达（Python urllib / PowerShell / curl 三条
  路径分别得到 Connection reset / 超时 / Recv failure，而同环境 github、pypi 正常）。
  v2.9.2 环境恢复后一次补齐，**结论从「5 个全部领先」变成「9 个 7 胜 2 负」** ——
  这个代价正是覆盖面变宽要付的。
- **单次运行**，无重复实验、无显著性检验。

## 复现

```bash
# 1. 下载数据集（PowerShell，约 13 MB）
$u = "https://zenodo.org/api/records/8275861"
$r = Invoke-RestMethod $u
foreach ($n in "Proxifier","Apache","Zookeeper","HealthApp","OpenStack") {
  Invoke-WebRequest ($r.files | ? { $_.key -eq "$n.zip" }).links.self `
    -OutFile "data/loghub/$n.zip"
  Expand-Archive "data/loghub/$n.zip" "data/loghub/$n"
}

# 1b. Android_v1 在另一个记录里 —— Loghub 1.0，不是 2.0
#     记录号 8275861（Loghub-2.0）里【没有】Android_v1，只有 Android_v2。
#     完整文件（23.7 MB / 解压 183.4 MB / 1,555,005 行）在 Loghub 1.0 的 8196385：
Invoke-WebRequest "https://zenodo.org/api/records/8196385/files/Android_v1.zip/content" `
  -OutFile "data/loghub/Android_v1.zip"
Expand-Archive "data/loghub/Android_v1.zip" "data/loghub_full/Android" -Force

# ⚠️ 这条链路在部分网络环境下会反复中途断流。下到一半的 zip 有合法
#    PK\x03\x04 头但没有 PK\x05\x06 中央目录，标准工具一律报
#    「找不到中央目录结尾记录」。判断方法：
#    [System.IO.Compression.ZipFile]::OpenRead($path)  能打开 = 完整
#    逐次重下无效时用 HTTP Range 断点续传，不要反复从头重来。
