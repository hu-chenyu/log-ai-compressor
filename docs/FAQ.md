## Q1 为什么不直接用 Drain3？它是学术标准（ICWS'17，800+★）

因为**两者优化的不是同一个量**。

同预算公平对照（`scripts/eval_budget.py`，Loghub 真实数据，
预算 = 输出 token 上限，看谁把根因证据留在了输出里）：

| 方法 | 200 | 400 | 800 | 1600 | 3200 | 6400 |
|---|---:|---:|---:|---:|---:|---:|
| `tail -N` | 0% | 0% | 0% | 0% | 0% | 0% |
| `grep` 关键词 | 0% | 0~40% | 0% | 40% | 40% | 60% |
| **Drain3** | 0% | 0% | **0%** | 0% | 40% | 100% |
| **log-ai-compressor** | 0% | 60% | **100%** | 100% | 100% | 100% |

- 同样 **800 token** 预算下，本项目保住 **100%** 的标注事件，Drain3 是 **0%**。
- Drain3 要到 **6400 token** 才追上 —— 本项目省 **8 倍**预算。
- 耗时也不落下风：HealthApp 上本项目 12.0s，Drain3 578.3s（**48 倍**）。

**为什么会有这么大的差距**：Drain 是为**日志模板抽取**设计的——
它的产出是一行模板 `connected to <:IP:>`。模板里没有时间戳、没有行号、
没有异常链。喂给 LLM 之后，"根因是什么"这个问题它答不了。
本项目产出的是**带行号区间和证据引用的排序结论**。

**本项目做不到的**：Drain3 的 Parsing Accuracy 是 99.75%（HDFS_2k），
本项目**不提供模板抽取，也不声称在这个指标上更强**。
这是两个品类，不该直接比 PA。

**怎么自己验**：
```bash
pip install drain3
python scripts/benchmark_loghub.py --datasets Apache --budgets 200,800,6400
```

## Q2 LogsLop（AMD）不也是干这个的吗？

是，而且它是**目前最接近的正面竞品**，2026-07 就在 ROCm 博客上公开了
（`pip install logslop`，`amd/logslop`）。它同样用 Loghub + Drain3 做对照，
并提出了 SURCL（Scroll-Until Root Cause Lines）指标，中位数 96 行 → 5 行。

**区别在于产出物的形态**：

| | LogsLop | log-ai-compressor |
|---|---|---|
| 做什么 | 逐行去重，丢掉重复行 | 聚类 + 置信分档 + 根因判定 |
| 指标 | SURCL（离末尾多远能滚到错误） | 证据保留率、精确率、**自信错误率**、召回率 |
| 能否说"我不知道" | 不涉及（它不做判定） | `INSUFFICIENT` 是合法输出 |
| 结论可复核 | 否（输出即文本） | 行号 + 原文 sha256，`verify` 可脱离本工具复核 |

LogsLop 解决的是"日志太长看不完"，本项目解决的是"**看完了也不敢下结论**"。
两者可以叠加使用。

## Q3 那直接让 LLM 读日志不行吗？LLMLingua 之类的提示压缩已经很成熟了

提示压缩确实成熟。**但提示压缩优化的是 token 数，本项目优化的是"结论是否可信"。**

LLMLingua（Microsoft Research, arXiv:2310.05736）能把 prompt 压 20 倍，
代价是它**必须用小模型去猜哪些 token 可以丢**。丢错了，你无从得知——
因为输出里没有"依据"这个概念。

本项目在两件事上和它正交：

1. **压缩前先做判定**：`CONFIRMED` 只在 Caused-by 链存在时才可能给出，
   拿不出链就是 `INSUFFICIENT` + 一份「还缺什么」的清单。这不需要任何模型。
2. **每条结论绑定原文摘要**：改一个字，sha256 就变，`verify` 立刻报失配。

一个工具可以说"根因是 X"却不告诉你 X 出自第几行——
那它的结论和 LLM 随口编的一句没有本质区别。**这是本项目存在的全部理由。**

## Q4 你的「自信错误率 0%」是不是把门槛设得太高了？

不是。它是**结构性的**，不是调参调出来的。

`CONFIRMED` 的唯一来源是条目内的 `Caused-by` 链。
代码里 `core/analysis.py` 的 `_causal_lines()` / `_has_caused_by()` 是唯一入口，
且**只有 `CONFIRMED` 档会去追 `deepest_caused_by`**。
没有链 → 最高只能到 `LIKELY`，`can_conclude=false`。

这条不变量由 `tests/test_forensics.py` 与对抗评测里的
`structured_trace_not_causal` 场景盯着。松了它，整条立场就作废了。

代价是召回：严格口径 Hadoop **91.4%**、Android_v1 **100%**。
**我们宁愿漏，不可乱说** —— 一个自信的错误根因比没有根因更糟，因为值班的人会照着它去查。

## Q5 证据引用能防篡改，那能防「结论本身就是错的」吗？

**不能。** 证据引用只保证"结论确实出自第几行的原文"，
它不保证"从这段原文推出的结论是对的"。

判据分三层，别混：

| 层 | 保证什么 | 谁保证 |
|---|---|---|
| 证据引用 | 结论指向的原文没被改过 | sha256 + `verify` |
| 确定性指纹 | 同一份输入两次跑结论逐字节相同 | `result_fingerprint` |
| 正确性 | 从原文到结论的推理是对的 | **没有人保证** —— 这正是要引入对抗评测和人工复核的原因 |

所以本项目**不声称**自己的根因判定等于人工判断。
它声称的是：给了你一条可复核、可复现、并且在拿不出证据时会闭嘴的推理链。

## Q6 压缩比 12289 倍，是不是挑了好看的口径？

**是，挑过。** 完整说清楚：

- 12289 倍是 **OpenStack 全级别摘要**口径：原始 15,299,983 tokens → 746。
- 换默认级别（只看 ERROR/FAIL），同一份数据的证据保留率从 100% 掉到 **10.4%**。
- 最差的一个数据集是 **OpenStack 证据保留率 50%**（全级别）——不是全胜。

所以这个数字的正确用法是：**说明上限，不是说明常态**。
日常用请看 §6.1 的逐数据集表，别只看最大的那个。

`docs/BENCHMARK.md` 里每一张表下面都写了「本文不能证明什么」，
包括"单次运行、无重复实验、无显著性检验"和"Thunderbird 等 300MB+ 数据集未测"。

## Q9 怎么自己验证这个项目没在吹？

三条命令，全在本地，不需要联网：

```bash
python scripts/prove.py            # 自证脚本：逐条核对本文每个对外主张，列出尚无数据的主张
python scripts/adversarial_eval.py # 对抗评测：10 个专门设计来误导本工具的场景
python -m pytest -q                # 904 个测试
```

`prove.py` 的设计原则是：**尚无数据的主张要显式列出来，不藏**。
它会打印「尚无数据的主张（刻意列出，不藏）」并逐条说明为什么现在给不出数字。
一个只敢公布准确率的工具，比一个敢公布自信错误率的工具可疑得多。
