## Q1 为什么不直接用 Drain3？它是学术标准（ICWS'17，800+★）

因为**两者优化的不是同一个量**。

同预算公平对照（`scripts/eval_budget.py`，Loghub 真实数据，
预算 = 输出 token 上限，看谁把根因证据留在了输出里）：

| 方法 | 200 | 400 | 800 | 1600 | 3200 | 6400 |
|---|---:|---:|---:|---:|---:|---:|
| `tail -N` | 0% | 0% | 0% | 0% | 0% | 0% |
| `grep` 关键词 | 0% | 0~40% | 0% | 40% | 40% | 60% |
| **Drain3** | 0% | 0% | **0%** | 0% | 40% | 100% |
| **log-ai-compressor** | 0% | 60% | **100%** | 100% | 100% | 100% |

- 同样 **800 token** 预算下，本项目保住 **100%** 的标注事件，Drain3 是 **0%**。
- Drain3 要到 **6400 token** 才追上 —— 本项目省 **8 倍**预算。
- 耗时也不落下风：HealthApp 上本项目 12.0s，Drain3 578.3s（**48 倍**）。

**为什么会有这么大的差距**：Drain 是为**日志模板抽取**设计的——
它的产出是一行模板 `connected to <:IP:>`。模板里没有时间戳、没有行号、
没有异常链。喂给 LLM 之后，"根因是什么"这个问题它答不了。
本项目产出的是**带行号区间和证据引用的排序结论**。

**本项目做不到的**：Drain3 的 Parsing Accuracy 是 99.75%（HDFS_2k），
本项目**不提供模板抽取，也不声称在这个指标上更强**。
这是两个品类，不该直接比 PA。

**怎么自己验**：
```bash
pip install drain3
python scripts/benchmark_loghub.py --datasets Apache --budgets 200,800,6400
```

## Q2 LogsLop（AMD）不也是干这个的吗？

是，而且它确实是**目前最接近的正面竞品**。v2.5.0 已经把它纳入实测对照
（`pip install logslop`，`amd/logslop`，2026-07 ROCm 博客；它同样用 Loghub +
Drain3 做对照，并提出 SURCL 指标）。实测证据保留率：

| 数据集 | 本项目(交付 top20) | **本项目(同预算 32k)** | 本项目(全量) | Drain3 | **LogsLop** |
|---|---:|---:|---:|---:|---:|
| Proxifier | 72.7% | **100.0%** | 100.0% | 72.7% | 27.3% |
| Apache | 55.2% | **100.0%** | 100.0% | 93.1% | 44.8% |
| OpenSSH | 36.8% | **92.1%** | 92.1% | 92.1% | 34.2% |
| Hadoop | 8.5% | **90.7%** | 90.7% | 80.5% | 13.1% |
| Zookeeper | 22.5% | **91.0%** | 91.0% | 76.4% | 23.6% |
| Linux | 2.4% | **89.3%** | 89.3% | 66.6% | 55.6% |
| HealthApp | 11.5% | **88.5%** | 88.5% | 83.3% | 7.1% |
| Mac | 3.2% | **90.4%** | 90.7% | 72.2% | 16.1% |
| HPC | 20.3% | **81.1%** | 81.1% | 87.8% | 4.1% |
| OpenStack | 37.5% | **52.1%** | 52.1% | 41.7% | 18.8% |

**对 Drain3：交付口径 0 胜 1 平 9 负 / 同预算 8 胜 1 平 1 负 / 全量 8 胜 1 平 1 负。**

这个 FAQ 的答案本来是「凭什么比 Drain3 强」，但**实测结果不支持「强」这个说法**，
所以这一节的标题改成「凭什么有时更强、有时更弱」。三件事说清楚：

1. **只剩一个数据集比不过它**（同预算档 HPC 81.1% vs 87.8%），我们没藏。
   Mac 曾是第二个负例（58.5% vs 72.2%），v2.9.8 修掉了。
2. **病因查到了「修法不存在」这一步**：
   - HPC 不是簇数不够，是**簇粒度比标注粗**。79 个簇只装下 60 种事件身份，
     **14 个未覆盖事件全部落在 12 个过度合并的簇上**，且无一例外只差一两个字面
     词元（`Link error`/`Link ok`、`critical`/`normal`、`boot`/`wait`/`risBoot`）。
     修法试过两次都失败：
     - **加字面词元守卫**：覆盖率从 85.1% 涨到 93.2%，**但报告从 76 个簇炸成
       2,690 个、交付口径从 23.0% 崩到 8.1%** —— 已撤回（指标涨了但产品崩了）。
     - **v2.10.0 换了问法**：把每一次合并决定都记下来（4,142 次），用 Loghub
       标注判对错，找能分开两类的特征。**没有这样的特征** —— 字符相似度与词元
       Jaccard 的两类分布完全重叠，Proxifier 甚至有 Jaccard = 1.000 的「错合并」。
       **Loghub 的事件定义不是模板相似度的函数**，所以这不是调参问题。
       可复算：`python scripts/diagnose_merge_decisions.py`。
   - Mac（v2.9.8 已修）：不是聚类丢事件（全量口径一直是赢的），
     而是报告把 406 条**错误消息**当成「变更事件」逐条写出，占全篇 33% token。
     收敛后同预算 58.5% → 82.9%。
   - Mac 在 v2.10.0 又从 82.9% 涨到 **90.4%**：相似度回退曾经只比级别桶里
     「最近 256 个簇」，长期只出现在桶尾之后的模板永远找不到同类
     （Mac 的 INFO 桶因此多出约 1,000 个碎片簇）。改成整桶比较 + 精确长度上界
     剪枝之后，INFO 桶 1,604 → 547 个簇，**分析还更快了（25.3s → 14.0s）**。
3. **胜负按事件种数判**，不按四舍五入后的百分数：报告只有 1 位小数，
   0.05pp 以内的差与舍入误差分不开，一律记平。OpenSSH 两边都是 35/38，**是平手**。
4. **这张表现在有门禁在守。** v2.9.9 改过 `mask_text`，让 HPC、Zookeeper、
   Proxifier 的数字全变了，而表和文档原地不动、六道门禁全绿。v2.10.0 加了
   `docs/benchmark_baseline.json` + `prove.py` 第 11 条主张做**逐格对账**，
   改了影响聚类的代码而不重跑全量基准，CI 会红。

> v2.9.4 这里曾写「严格档 10 胜 0 平 0 负」。**该结论已于 v2.9.5 撤回** ——
> 当时的覆盖率在数报告里根本没出现的簇。撤回经过与三次同形的测量 bug，
> 见 [BENCHMARK.md](BENCHMARK.md) 的「v2.9.5 撤回经过」一节。

LogsLop 在全部 10 个数据集上都落后于 Drain3，也落后于本项目。

对照口径对它是公平的，不是为了让它输：

- 喂**原始日志行**，因为这是它自己文档与博客里的标准用法
  （Drain3 要剥离结构化头，是因为模板抽取需要；对照时给各自应得的输入才公平）
- 它保留的也是原始行，能按 LineId 精确回查，与 tail / grep / 本项目同一映射口径，
  不存在 Drain3 那种「模板相似度 ≥0.8 模糊匹配」的余地
- 标注覆盖率实测 **100%**（每个数据集每一行都有 EventId），不是标注稀疏造成的低估

**它弱在哪**：LogsLop 优化的是「别让我看两遍一样的东西」（去重），
证据保留要的是「别弄丢我的根因证据」。**这两个目标方向相反** ——
文本长得像的不同事件会被合并掉。而且它**几乎不随预算增长**：
Apache 上从 @500tok 的 37.9% 到 @32k 仍是 44.8%，给再多 token 也救不回被合并的事件。

**怎么自己验**：
```bash
pip install logslop
python scripts/benchmark_loghub.py --datasets Apache
```

## Q3 那直接让 LLM 读日志不行吗？LLMLingua 之类的提示压缩已经很成熟了

提示压缩确实成熟。**但提示压缩优化的是 token 数，本项目优化的是"结论是否可信"。**

LLMLingua（Microsoft Research, arXiv:2310.05736）能把 prompt 压 20 倍，
代价是它**必须用小模型去猜哪些 token 可以丢**。丢错了，你无从得知——
因为输出里没有"依据"这个概念。

本项目在两件事上和它正交：

1. **压缩前先做判定**：`CONFIRMED` 只在 Caused-by 链存在时才可能给出，
   拿不出链就是 `INSUFFICIENT` + 一份「还缺什么」的清单。这不需要任何模型。
2. **每条结论绑定原文摘要**：改一个字，sha256 就变，`verify` 立刻报失配。

一个工具可以说"根因是 X"却不告诉你 X 出自第几行——
那它的结论和 LLM 随口编的一句没有本质区别。**这是本项目存在的全部理由。**

## Q4 你的「自信错误率 0%」是不是把门槛设得太高了？

不是。它是**结构性的**，不是调参调出来的。

`CONFIRMED` 的唯一来源是条目内的 `Caused-by` 链。
代码里 `core/analysis.py` 的 `_causal_lines()` / `_has_caused_by()` 是唯一入口，
且**只有 `CONFIRMED` 档会去追 `deepest_caused_by`**。
没有链 → 最高只能到 `LIKELY`，`can_conclude=false`。

这条不变量由 `tests/test_forensics.py` 与对抗评测里的
`structured_trace_not_causal` 场景盯着。松了它，整条立场就作废了。

代价是召回：Android_v1 全量（131 条链）**报告口径 100%**。
**我们宁愿漏，不可乱说** —— 一个自信的错误根因比没有根因更糟，因为值班的人会照着它去查。

## Q5 证据引用能防篡改，那能防「结论本身就是错的」吗？

**不能。** 证据引用只保证"结论确实出自第几行的原文"，
它不保证"从这段原文推出的结论是对的"。

判据分三层，别混：

| 层 | 保证什么 | 谁保证 |
|---|---|---|
| 证据引用 | 结论指向的原文没被改过 | sha256 + `verify` |
| 确定性指纹 | 同一份输入两次跑结论逐字节相同 | `result_fingerprint` |
| 正确性 | 从原文到结论的推理是对的 | **没有人保证** —— 这正是要引入对抗评测和人工复核的原因 |

所以本项目**不声称**自己的根因判定等于人工判断。
它声称的是：给了你一条可复核、可复现、并且在拿不出证据时会闭嘴的推理链。

## Q6 压缩比两万倍，是不是挑了好看的口径？

**是，挑过。** 完整说清楚：

- **压缩比 20,509 倍**是 **OpenStack 全级别摘要**口径：原始 15,299,983 tokens → 746
  （15,299,983 ÷ 746 ≈ 20,509，两个数都取自
  [`docs/BENCHMARK.md`](BENCHMARK.md) 的 token 压缩表）。
- 换默认级别（只看 ERROR/FAIL），同一份数据的证据保留率从 100% 掉到 **10.4%**。
- 最差的一个数据集是 **OpenStack 证据保留率 50%**（全级别）——不是全胜。

所以这个数字的正确用法是：**说明上限，不是说明常态**。
日常用请看 README 里那张逐数据集的保留率表，别只看最大的那个。

`docs/BENCHMARK.md` 里每一张表下面都写了「本文不能证明什么」，
包括"单次运行、无重复实验、无显著性检验"和"Thunderbird 等 300MB+ 数据集未测"。

## Q9 怎么自己验证这个项目没在吹？

三条命令，全在本地，不需要联网：

```bash
python scripts/prove.py            # 自证脚本：逐条核对本文每个对外主张，列出尚无数据的主张
python scripts/adversarial_eval.py # 对抗评测：10 个专门设计来误导本工具的场景
python -m pytest -q                # 1,449 个测试
```

`prove.py` 的设计原则是：**尚无数据的主张要显式列出来，不藏**。
它会打印「尚无数据的主张（刻意列出，不藏）」并逐条说明为什么现在给不出数字。
一个只敢公布准确率的工具，比一个敢公布自信错误率的工具可疑得多。

## Q11 一个簇里有好几个不同的根因时，你报哪一个？

**v2.7.0 已修：全部报出来，主因写进根因行，其余按次数列成变体清单。**

v2.6.0 之前是**报样例那一个，其余静默丢掉**。这是用最小用例复现出来的真缺陷，
不是我推演出来的：

```
2024-01-15 10:00:00 ERROR java.lang.RuntimeException: a failed
Caused by: com.acme.First: root of it
2024-01-15 10:00:01 ERROR java.lang.RuntimeException: b failed
Caused by: com.acme.Second: root of it
```

两条外层消息一词之差 → 聚成同一簇 → `count=2`、两个实例各带一条 Caused-by，
但 `root_cause_reason` 只写了 `com.acme.First`。**`com.acme.Second` 的链没人提。**

### 修法与取舍

「报最多的？全列？按实例拆簇？」三种改法里，我选了**全列**：

- **拆簇**要改簇边界，会动到「同输入同结论」之外的一堆不变式，风险最大；
- **只报最多的**仍然会丢信息 —— 那个「次多的」依然是日志里确凿的因果链；
- **全列**不动簇边界，也不动 CONFIRMED 的定义（根因仍只来自条目内 Caused-by 链）。

现在同一个簇会给出：

```
根因判定：是（Caused-by 因果链直连，根因：com.acme.First: root of it（本簇 2 种内层因，主因 1/2 次））
簇内全部内层因：com.acme.First: root of it × 1（主因）；com.acme.Second: root of it × 1
```

**每种内层因都带自己那一处原文引用**（`L1-L2` 与 `L5-L6`，指向各自那条链），
`verify_evidence` 全部回读通过。一条指向别处的"证据"比没有证据更危险 ——
排查的人会照着它去核对日志，核不到，整份报告的可信度一起塌。

### 两个实现上必须诚实的地方

1. **计数覆盖全量输入，不是样本**。簇内实例详情每簇只留前 200 条
   （`MAX_CLUSTER_INSTANCES_DETAILED`），靠实例反推只能拿到有偏样本 ——
   那正是 v2.6.0 缺陷的成因。所以改成**摄入期流式累计**（每条带链的条目
   入簇就记一次），计数与实例保留上限彻底解耦。
2. **单簇内层因种类上限 32 种**（`MAX_CAUSES_PER_CLUSTER`），超出部分计入
   `cause_overflow`，报告里写明「另有 N 次未展开」，不静默丢弃。

### 「严格召回 100%」的可信度

**Android 全量上有几个多因簇？答案是 0。** 实测普查（v2.7.0，10,752 个簇）：
10 个带因果链的簇，**内层因种类数分布 `{1: 10}`** —— 每个簇只有一种内层因。

所以必须说清楚三件事：

1. **Android 从来没有执行过这条新路径**。修复前后，报告口径都是 **131/131**，
   变体救回 **0 条链**（同一份分析、只换「报告文本」的取法实测过）。
2. **修的是正确性，不是指标**。别把「修完数字没变」读成「这修复没用」，
   也别读成「Android 验证了它」—— 它没有。
3. **证据是单元测试与最小复现，不是这个数据集**。Android 的 131/131 在
   修复前后一致，这个数字本身没受影响；受影响的是那些**簇内确有多个内层因、
   且少数内层因没有被别的 CONFIRMED 簇覆盖**的输入 —— 而 Loghub 现有数据里
   恰好没有这种形状（本地所有 Loghub 日志逐文件实测 `Caused by` 全为 0，
   只有 Android_v1 有链）。

**这条教训比修复本身更值钱**：一个数据集没覆盖到某个形状，会让人以为那条
形状不存在。所以我把「Android 多因簇 = 0」这件事也写出来，而不是让读者
默认「测过了、没事」。

Q10 撤掉的那个旧口径还有一个更隐蔽的问题：**它检测不出这个缺陷**。
旧口径查的是「簇的**样例原文**里有没有出现过这个类名」，而一个簇的样例
恰好是 `SocketException` 时，后面 29 次同类的链全被算作"被点名" ——
可报告里根因那一行写的是另一个类。**用户照着报告查，报告里没有。**

所以 `eval_rootcause.py` 在 v2.7.0 加了**报告口径**：要求簇**对外报告的根因文本**
（`root_cause_reason` + 全部变体）点名该链的根因类名，只有这个口径才对外。
顺手还修了脚本自身一个 bug —— 它读的是 `entry.stack_lines`，而模型字段叫
`entry.stack`，属性名写错导致这个口径**从来没看过堆栈**，指标不报错不告警，
只是安静地退化。**指标看不见自己该管的缺陷，比指标偏低更危险。**

**怎么自己验**：
```bash
python -m pytest tests/test_orphan_cause_robustness.py tests/test_cause_variant_exports.py -v
python scripts/eval_rootcause.py --repro        # 三个口径都打，对外只认报告口径
```
