# 对抗性评测与置信档位实测

## 对抗性评测：专门设计来误导这个工具的场景

上面所有数字都由本项目自己产出，所以另配了一组**专门用来让本工具出错**的
场景，按四条硬规则打分。这是本项目唯一能证明自己没在自说自话的方式。

```console
$ python scripts/adversarial_eval.py
● structured_trace_not_causal   [4/4]  verdict=LIKELY  簇=3 CONFIRMED=0
  ✓ abstain_correctly       verdict=LIKELY, can_conclude=False, CONFIRMED 簇 0 个
  ✓ causal_language_ok      非 CONFIRMED 簇未使用因果措辞
  ✓ trace_chain_found       最长链路覆盖 3 个服务（要求 ≥3）
  …
────────────────────────────────────────────────────────────
  场景数              : 10
  评分项 / 通过        : 35/35  (100.0%)
  正确弃权率           : 100.0%  （5 个应弃权场景）
  自信错误率           : 0.0%    ← 最该压到 0 的那个数
  总判定               : PASS
```

10 个场景包括：红鲱鱼部署、关键词堆砌的良性日志、共现无因果、单模块无栈、
无时间戳、**反向**场景（证据其实够了，不该虚报缺口）、结构化日志调用链、
**有完整调用链但无 Caused-by**、以及普通文本被误吞成 logfmt。

两条口径写死在脚本里，评审前先看这两条：

- **弃权算通过，不算失败。** 在确实无法定论的事件上正确弃权是这个工具想要
  的行为。只算命中率的评测会偏好猜得最自信的系统 —— 那正是要淘汰的。
- **自信错误率权重最高。** 值班的人会照着一个自信的错误根因去排查。

这套评测已经抓出过真 bug：原实现把「时间上紧邻在前的另一个错误簇」当成
因果因，标成 CONFIRMED，一条 `INFO request started` 因此被判成确定性根因。

**已接入 CI**（`.github/workflows/ci.yml`）：评分卡不过，CI 变红。

### 置信档位实测：零因果链时零确定性断言

「敢不敢说我不知道」这句话需要数据支撑。评测方式：**完全独立于本项目**，
直接扫原始日志的 `Caused by:` 链构造地面真相，再与工具输出对账。

| 数据集 | 行数 | 真实因果链 | 工具判 CONFIRMED | 自信错误率 |
|---|---:|---:|---:|---:|
| Zookeeper | 74,273 | 0 | **0** | **0%** |
| 其余 4 个 | 455,324 | 0 | **0** | **0%** |

**这个评测第一跑就抓到一个真 bug**：原实现把「时间上紧邻在前的另一个错误
簇」当成因果因，然后标成 CONFIRMED —— 一条 `INFO request started` 因此
被判成确定性根因，正是这个功能声称要消灭的「自信的错误答案」。已修复为
只认条目内 `Caused by:` 链，并把根因指向链上最内层的异常。

**召回率（真出现因果链时能否找到）**：复现语料（自建故障场景 + 真实 Java
异常/栈帧/日志格式，**非生产日志**）上已可复跑 —— 5 条因果链，精确率 100%、
召回率 100%、自信错误率 0%，无链对照组 0 CONFIRMED：

```console
$ python scripts/eval_rootcause.py --repro
  合计：真实因果链 5，CONFIRMED 5
    精确率 100.0%   自信错误率 0.0%   召回率 100.0%
```

**真实数据集：一个，全量可复现**

| 数据集 | 含链文件 | 真实链 | CONFIRMED | 精确率 | 自信错误率 | 召回率·报告口径 |
|---|---:|---:|---:|---:|---:|---:|
| Loghub **Android_v1**（全量 1,555,005 行） | 1 | 131 | 10 | 100.0% | 0.0% | **100.0%** |

```console
$ python scripts/eval_rootcause.py
  合计：真实因果链 131，CONFIRMED 10
    精确率 100.0%   自信错误率 0.0%
    召回率·报告口径 100.0% (131/131)
    召回率·簇文本 100.0% (131/131)
    召回率·宽松 100.0% (131/131)
```

> **v2.7.0 撤回了一组数字：Loghub Hadoop 的 91.4%。** 那份数据的来源已确认
> 不可得 —— 两个 Zenodo 记录、`logpai/loghub` 仓库、本项目 `data/` 下全部真实
> 日志都查过，均无 YARN / `application_*/container_*.log`，且本地每个 Loghub
> 日志逐文件实测 `Caused by` 出现次数为 0（只有 Android_v1 有链）。一个跑不
> 出来的数字留着只会在被追问时塌台。撤回经过见
> [`docs/BENCHMARK.md`](docs/BENCHMARK.md) 与 [`FAQ.md` Q10](docs/FAQ.md)。

**三个召回口径必须说清差别**：**报告口径（对外只认这个）**要求 CONFIRMED 簇
**对外报告的根因文本**（`root_cause_reason` + 全部内层因变体）点名该链的根因
类名 —— 答的是「用户照着报告能不能查到这一条」；**簇文本**只查簇的**样例原文**
里有没有出现过这个类名（文本里有过 ≠ 工具把它说了出来）；**宽松**只要求行区间
盖住，只证明位置对得上。

v2.7.0 把对外口径换成「报告口径」的理由：旧口径查的是样例原文，而一个簇的样例
恰好是 `SocketException` 时，后面 29 次同类的链全被算作"被点名"，可报告里根因
那一行写的是另一个类 —— **用户照着报告查，报告里没有**。更要紧的是，旧口径
**检测不出 v2.6.0 那个「一簇只报一因」缺陷**（变体不存在，簇文本照样满分）。
**指标看不见自己该管的缺陷，比指标偏低更危险。**

**Android_v1 那一行是被真实 bug 逼出来的**：最初实测召回率是 **0%**（131 条真实
链、CONFIRMED 零个）。根因是 Android logcat 把整个异常压在一行里
（`E Tag: com.x.PushException: boom Caused by: java.net.SocketException: abort`），
而本工具既没有 logcat 解析模式（无年份 / 单字母级别 / PID+TID），`Caused by` 的
两条正则也都锚在行首 —— 链**整条看不见**。现在两种形态都认，
见 [`docs/BENCHMARK.md`](docs/BENCHMARK.md) 与 CHANGELOG 2.3.0。

**样本限制照实说**：

- **Android_v1 在 v2.4.0 已补跑全量** —— 1,555,005 行 / 131 条链，链密度与原文件
  一致（1 / 11,870 行），报告口径召回 **100%**。原先切片时那条「密度高 6.8 倍、
  方向偏保守」的免责声明已删除，因为**结论没有随密度回落而翻转**。
- **Hadoop 那组数字已在 v2.7.0 撤回** —— 数据集来源不可得（两个 Zenodo 记录、
  `logpai/loghub` 仓库、本地全部数据都查过），且本地每个 Loghub 日志逐文件实测
  `Caused by` 出现次数为 0。撤回经过见
  [`docs/BENCHMARK.md`](docs/BENCHMARK.md)。
- **只有一个含链的真实数据集** —— 这是本项目最实在的一条短板，且代码解决不了：
  131 条链、8 个根因类，样本量不大，「召回 100%」不能外推到别的日志形态。

复现语料与真实数据分开列，不混。

复现：`python scripts/benchmark_loghub.py` ·
`python scripts/eval_rootcause.py <日志路径>` ·
`python scripts/eval_rootcause.py --repro` ·
完整方法学、对照组公平性说明与「本文档不能证明什么」见 [`docs/BENCHMARK.md`](docs/BENCHMARK.md)
